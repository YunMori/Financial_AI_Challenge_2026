### 1. 부록 B2 — 한도제한계좌 한도가 거래유형별로 다르다

| | |
|---|---|
| 기획서 값 | "1일 한도 100만 원 (2024.5.2~)" |
| **실제** | **인터넷뱅킹 100만 · ATM 100만 · 창구 300만 원** |

| 조치 | 거래유형을 명시. 상향 전 값(30/30/100)도 함께 쓰면 개선 효과가 드러난다 |

**은행별 시행일 차이**도 함께 기재: 농협·하나·부산은행은 2024-05-10.
데모 시나리오 2("왜 100만 원까지만")는 전자금융 맥락이라 **시나리오 자체는 유효**하다.

### 2. §3장 — "체류외국인"과 "등록외국인"을 혼용하면 안 된다

| | |
|---|---|

### 3. planner §6.3 — 체류자격 정규식이 작동하지 않는다

```python
# 원안 — 한국어 조사 앞에서 매칭 실패
VISA_RE = re.compile(r"\b([A-H]-\d{1,2})\b")
```

| 입력 | 원안 | 수정본 |
|---|---|---|
| `E-9 비자입니다` | `['E9']` | `['E9']` |
| `E-9인데요` | **`[]`** | `['E9']` |
| `E-7과 E-9의 차이` | **`[]`** | `['E7','E9']` |
| `E9 비자 계좌개설` | **`[]`** | `['E9']` |

**기획서 §8.3의 "BM25는 E-9와 E-7을 완전히 다른 토큰으로 취급한다"는 서술의
근거가 원안대로면 성립하지 않는다.** 수정본:
`r"(?<![A-Za-z0-9])([A-H]-?\d{1,2})(?![0-9])"` + `IGNORECASE`.
회귀 케이스 17개 고정 (`tests/test_tokenize.py`).

> **일반 규칙으로 승격**: 한국어 텍스트에 정규식 뒤쪽 경계(`\b`, `(?![\w])`)를
> 쓰지 않는다. 같은 원인의 버그를 체류자격·수량·PII 세 곳에서 만났다.

### 4. planner §6.6 — `threshold_top1 = 0.42` 는 폴백을 한 번도 걸지 못한다

e5 코사인 유사도는 **0.76~0.91** 구간에 몰린다. 0.42 로는 검색 신뢰도 방어가
통째로 죽어 있다. 실측 보정값 **0.839** (코퍼스 안 최소 0.8494 / 밖 최대 0.8293).
`python -m app.rag.cli --calibrate` 로 재현 가능.

### 5. planner §6.6 — `threshold_margin = 0.05` 는 모든 질의를 폴백시킨다

실측 margin 최대값이 0.017 이다. 더 근본적으로, **RRF margin 은 신뢰도 신호가
아니다** — 코퍼스 *밖* 질의가 오히려 높은 margin(0.0167)을 냈다. "두 검색기가
같은 문서를 골랐는가"를 재는 값이라 근거 존재 여부와 무관하다.
→ 비활성화(0.0). 대체 신호는 골든셋과 함께 설계.

### 18. ★ 코퍼스 확장이 임계값을 깨뜨린다 — 검색 신뢰도는 코퍼스에 종속된다

기획서·planner 는 임계값을 **한 번 정하는 상수**로 다룬다. 실측은 반대다.

| | 코퍼스 26청크 | 71청크 |
|---|---:|---:|
| 코퍼스 **안** 최소 | 0.8494 | 0.8600 |
| 코퍼스 **밖** 최대 | 0.8293 | **0.8416** |
| 임계값 | 0.839 | **0.851** |

한도제한계좌 문서를 늘렸더니 **코퍼스 밖 질의인 "전세자금대출 한도"가
0.8296 → 0.8416 으로 올라 옛 임계값을 넘어섰다.** 그 상태로 두면 전세자금대출
질문에 폴백이 걸리지 않고 엉뚱한 근거로 답한다.

**조치**: 임계값을 상수가 아니라 **코퍼스의 함수**로 서술한다. 문서를 추가할
때마다 `python -m app.rag.cli --calibrate` 를 돌리는 것을 수집 절차에 넣는다.

### 19. ★★ 베트남어는 검색 신뢰도 판정이 성립하지 않는다

2026-08-12 언어별 실측 (`--calibrate` 를 ko/en/vi 로 확장):

| 언어 | 코퍼스 안 최소 | 코퍼스 밖 최대 | 분리 폭 |
|---|---:|---:|---:|
| ko | 0.8600 | 0.8416 | +0.0184 |
| en | 0.7969 | 0.7841 | +0.0128 |
| **vi** | **0.7956** | **0.7961** | **−0.0005** |

베트남어는 **근거가 있는 질문이 없는 질문보다 낮게 나온다.** 어떤 임계값도
"정상 질문을 막지 않으면서 무관한 질의를 거르는" 일을 못 한다.

기획서 §11.4 가 `low_confidence` 폴백을 **모든 언어에 동일하게 동작하는 안전
장치**로 서술했다면 그 서술은 성립하지 않는다. 현재 vi 값 0.790 은 "무관한
질의를 통과시키더라도 정상 질문은 막지 않는" 쪽을 택한 것이지 안전한 값이 아니다.

**단, 이 측정은 API 키가 없어 질의 정규화(②)가 꺼진 상태다.** 번역이 살아나면
베트남어 질의가 한국어 검색어로 바뀌어 한국어 척도에서 채점되므로 분리가
되살아날 가능성이 크다. → Phase A 직후 재측정. 그래도 겹치면 리랭킹은 품질
개선책이 아니라 **비한국어 이용자를 위한 필수 안전장치**다(ADR-001).

> #### ✅ 해소됨 (2026-08-12, 키 확보 후 재측정)
>
> 가설이 맞았다. 번역이 켜지자 베트남어 점수가 한국어 척도로 올라왔다.
>
> | | 번역 꺼짐 | 번역 켜짐 |
> |---|---:|---:|
> | vi 코퍼스 안 최소 | 0.7956 | **0.8520** |
> | vi 분리 폭 (무근거 기준) | −0.0005 | **+0.0199** |
>
> 그리고 **관계가 뒤집혔다.** 번역 전에는 비한국어 점수가 체계적으로 낮아
> 임계값을 낮게 뒀는데, 번역 후에는 오히려 **높다**(번역된 검색어가 문서
> 어휘에 더 가깝게 정제되기 때문). 기획서 §11.4 에 "비한국어는 임계값을
> 낮춘다"고 적었다면 그 서술도 함께 뒤집어야 한다 — 현재 값은
> ko 0.8246 < vi 0.8321 < en 0.8445 다.
>
> 리랭킹을 "비한국어 필수 안전장치"로 앞당길 이유는 사라졌다 → ADR-001 은
> **리랭킹 미도입**으로 확정됐다.

### 22. ★★ 신뢰도 게이트를 잘못된 과녁에 맞추고 있었다

기획서·planner 는 `low_confidence` 폴백을 "근거가 약하면 막는 장치"로
서술하면서, 검증에서는 **계층 C 함정까지 이 게이트로 막으려 했다.**

두 가지는 성질이 다르다.

| 종류 | 예 | 검색 점수 | 누가 막아야 하는가 |
|---|---|---|---|
| 근거 없음 | "외국인 운전면허 절차" | 낮다 | **신뢰도 게이트** |
| 계층 C | "제 소득이면 한도가 얼마인가요" | **높다(정상)** | ②규칙 · ⑨계층 판정 |

계층 C 함정은 **주제상 관련이 있어** 검색 점수가 높게 나오는 것이 정상이다.
그걸 게이트로 막으려고 임계값을 올리니 정상 질의가 함께 죽었다 —
**과잉폴백 33.8%**(exp_002). 과녁을 바로잡아 재보정하니 `low_confidence`
과잉폴백이 9건 → 3건으로 줄었다(exp_003).

계층 C 는 이미 다른 두 곳이 잡고 있었다: 폴백 정확도 **100%**(35/35),
정규식 우회 표현도 **100%**(13/13).

**조치**: 기획서에서 `low_confidence` 의 책임 범위를 **"근거 없음"으로 한정**해
서술하고, 계층 C 차단은 ②·⑨의 몫으로 분리해 적는다. 임계값 보정 절차도
"코퍼스 밖 질의"가 아니라 **"근거 없는 질의"** 로 대상을 명시한다.

**대가도 같이 적는다**: 임계값을 낮추면 함정이 생성 단계까지 도달한다.
실측에서 10건 중 9건은 계층 판정이 잡았고 **1건이 새어 나갔다**
(`"월급 300만원인데 한도 풀 수 있나요?"` → 계층 B). 폴백 정확도는 97.1% 로
목표(≥95%)를 지키지만 100% 는 아니다.

### 23. ★★ 숫자 대조가 한국어 표기만 이해한다 — 다국어 서비스인데

기획서 §7.4·§8.3 은 숫자 대조를 **환각 방어의 핵심**으로 서술한다. 실제로는
답변이 나가는 세 언어 중 **둘에서 제대로 동작하지 않았다.**

| 표기 | 파싱 결과 | 실제 값 |
|---|---:|---:|
| `3.000.000 won` (베트남어·유럽식) | **3** | 3,000,000 |
| `30 million won` | **30** | 30,000,000 |

천단위 점을 소수점으로 읽어 **1,000,000 배 틀린 값**이 나왔다. 위험이 양방향이다 —
근거에 `3` 이 있으면 틀린 금액이 통과하고, 없으면 정상 답변이 차단된다.
실측(exp_003)에서 과잉폴백 14건 중 **9건이 이 원인**이었다.

**조치**: 기획서에서 숫자 대조를 서술할 때 **표기 정규화의 대상 언어를 명시**한다.
"1,000,000원 / 100만원 / 백만원" 만 예로 드는 현재 서술은 한국어 전용 장치처럼
읽힌다. 실제로 지원해야 하는 것은 공개 언어 전부다.

### 24. ★★★ 계층 C 차단이 베트남어에서 동작하지 않았다

기획서 §7·§8 은 계층 C 차단(개별 심사·추천·사기 판정 거절)을 **모든 공개
언어에서 동일하게 동작하는 안전장치**로 서술한다. 실제로는 `rules.py` 의
패턴이 **한국어와 영어뿐**이었고, 베트남어는 "정규화 후 한국어 검색어로
2차 방어"에 의존하고 있었다. 정규화는 검색어를 만드는 것이지 의도를
보존하지 않으므로 그 방어는 성립하지 않는다.

골든셋을 160문항(vi 41건)으로 늘리자 드러났다 — vi 함정 3건이 **계층 A**,
즉 확신을 갖고 답변됐다.

| 질문 | 결과 |
|---|---|
| "Ngân hàng nào tốt nhất cho người nước ngoài?" (어느 은행이 제일 좋나요) | 계층 A |
| "Tôi nên chọn ngân hàng nào?" (어느 은행을 골라야 하나요) | 계층 A |
| "tin nhắn nói tài khoản bị khóa, có thật không?" (이 문자 진짜인가요) | 계층 A |

영어도 사기 판정 패턴이 `scam|phishing|fraud` **단어를 요구**해
`"is it real?"` 형태를 놓쳤다. 이용자는 "사기인가요"보다 "진짜인가요"라고 묻는다.

**주 이용자가 비한국어 화자인 서비스에서, 핵심 거절이 주 이용자 언어에서
동작하지 않았다.**

**조치**: 기획서에서 계층 C 차단을 서술할 때 **언어별 구현 현황을 명시**한다.
"규칙으로 차단한다"는 서술은 언어를 밝히지 않으면 과대 서술이다. 공개 언어를
늘릴 때마다 규칙·골든셋을 함께 늘리는 것을 절차에 넣는다
(원어민 검수 원칙 §10.3 과 같은 성질의 제약).

## 🟠 설계 불가 — 대안으로 교체

### 20. HWP 를 읽지 못하면 1차 출처를 놓친다 — 그리고 PDF 판이 더 나쁠 수 있다

금융위 82205 보도자료의 PDF 첨부에서 **pdfplumber 가 '개선방안' 열을 통째로
놓쳤다.** 남은 것은 상향 *전* 값이다:

```
| 창구 | | 100만원 | |      ← 300만원 소실
| ATM | 인출 | 30만원 | |   ← 100만원 소실
```

이 프로젝트에서 가장 자주 인용될 숫자(B2)의 표가, **틀린 값을 담은 채로**
색인에 들어가 있었다. "창구에서 얼마까지 되나요"에 2024년 이전 값이 인용될
수 있었다는 뜻이다. 산문에는 올바른 값이 있어 fact-check 는 통과했다 —
**표만 조용히 틀린 것**이라 사람 검토를 빠져나갔다.

→ `02_clean` 에 HWP 5.0 추출기를 넣었다. HWP 는 셀마다 (열, 행, 병합)을 레코드로
갖고 있어 **표 복원이 PDF 보다 정확하다.** 셀을 순서대로 잇지 않고 좌표에
배치해야 한다 — 병합이 있는 표를 순서대로 이으면 값이 밀려 다른 행의 숫자를 읽는다.

함께 넣은 방어:
- `empty_columns()` — 표의 한 열이 통째로 비면 경고. 첫 열은 제외한다(세로 병합이
  흔해 오탐 5건 중 4건이었다). **늘 울리는 경보는 곧 무시된다.**
- `near_duplicates()` — 같은 보도자료가 HTML·PDF·HWP·교육란·정책브리핑
  **5중으로** 들어와 있었다. 상위 5건이 한 문서의 사본이면 다른 근거가 밀려나고,
  같은 문서를 여러 번 맞히므로 **Recall 이 실제보다 좋아 보인다.**

### 21. 국내 기관 페이지는 인코딩이 섞여 있다

은행연합회 소비자포털은 한 파일 안에 템플릿이 UTF-8, 본문이 CP949 이고
meta 태그에 `charset="UTF-8"` 과 `charset=euc-kr` 을 **둘 다** 달고 있다.
UTF-8 로 못박고 `errors="replace"` 를 쓰면 예외 없이 통과하면서 본문이 전부
깨진 글자가 된다 — 실제로 그 상태로 한 번 색인됐다.

→ 후보 인코딩마다 디코딩해 **깨진 글자가 가장 적은 것**을 고른다. 선언도
엄격 디코딩도 믿을 수 없기 때문이다.


### 6. §15.2 — 국내 리전 원칙(`LLM_REGION=kr`)은 충족 불가

Anthropic API 는 해외 리전이다. 문구를 덮지 말고 **더 정확한 서술로 교체**:

> 임베딩·벡터DB·BM25·입출력 가드레일·계층 판정이 전부 로컬에서 실행되고,
> 외부로 나가는 것은 **생성 호출 하나뿐**이다.

축소가 아니라 강화다 — 안전 속성이 전부 로컬 코드에 있으므로 모델을 바꿔도
유지된다. 근거: `docs/adr/ADR-002-llm-selection.md`

### 7. §2.2 — BGE-m3 를 쓸 수 없다

fastembed 가 BGE-m3 를 지원하지 않는다(2026-08 기준). `sentence-transformers`
(torch)를 쓰면 이미지·메모리가 더 커지는데, 이미 메모리가 한계다.
→ `intfloat/multilingual-e5-large` 채택. 근거: `docs/adr/ADR-003-embedding.md`

### 8. §15.3 — Render 스타터(512MB)로는 배포할 수 없다

컨테이너 실측: 유휴 46 MiB → 첫 질의 후 **1,979 MiB** → 피크 **2,096 MiB**.
**Standard(2GB) 이상 필수**이며 피크가 2,048 MiB 를 근소하게 넘는다.

작은 모델로 내려가는 것은 **안전장치를 없애는 일**이다:

| 모델 | RSS | 코퍼스 안/밖 분리 |
|---|---:|---:|
| e5-large | 1,510 MiB | **+0.0200** |
| MiniLM | 820 MiB | **−0.2742** (역전) |

MiniLM 에서는 `low_confidence` 폴백 판정이 원리적으로 불가능해진다.

### 9. §2.3 — 프로바이더 2종 병행 대신 모델 2종 폴백

키가 하나뿐이고, 계정·평가를 두 배로 늘리는 비용 대비 이득이 없다.
`claude-sonnet-5` → `claude-opus-5` (성공률 우선, 위로 올림).

### 17. 수집 파이프라인 — 정부 카드뉴스는 본문이 통째로 중복된다

`korea.kr` 카드뉴스는 슬라이드 이미지의 대체 텍스트와 본문이 함께 추출되면서
**같은 내용이 두 번** 들어온다. 실측:

| 문서 | 중복 제거 전 | 후 | 비율 |
|---|---:|---:|---:|
| KOREA-PHISHING-GUIDE | 1,021자 | 486자 | **52%** |
| KOREA-2024-0502-LIMIT-BRIEF | 1,605자 | 817자 | **49%** |

두 번째 문서는 **M1부터 색인에 들어가 있던 P0 문서**다. 손해가 두 겹이다 —
같은 문장이 두 번 든 청크는 그만큼 근거를 덜 담고, **BM25 는 단순 빈도를 쓰므로
중복된 문서가 부당하게 높은 점수를 받는다.** 검색 품질을 재기 전에 잡아야 했던
결함이고, 골든셋 측정 후에 발견했다면 원인 추적이 훨씬 어려웠다.

→ `02_clean.dedupe_repeats()` 추가. 연속 반복 줄 + 앞에 나온 3줄 이상 블록을
제거한다. **표(`|` 포함)는 건드리지 않는다** — 값이 같은 행이 실제로 존재할 수
있고, 표를 한 청크에 보존하는 것이 `03_chunk` 의 전제다.

## 🟡 서술 보강

### 10. 부록 B10 — 보이스피싱 통계의 유형 범위

확보한 경찰청 자료는 **기관사칭형·대출사기형 2종만** 집계한다.
"보이스피싱 전체"로 서술하려면 각주로 범위를 밝혀야 한다.
(2025년 합계 23,360건 / 12,578억 원은 기획서 값과 **일치**)

### 11. 부록 B7 — 발급일과 금융 이용 개시일이 다르다

- 모바일 외국인등록증 **발급** 시작: 2025-01-10 (법무부)
- **금융거래 이용** 개시: 2025-03-21 (금융위, 6개 은행)

은행 명단 확보: 신한·하나·아이엠뱅크·부산·전북·제주.
이 중 **신한·전북은 비대면**도 가능. 시점 표기 필요 — 이후 늘었을 수 있다.

### 12. §11.4 — 언어별 검색 임계값이 필요하다 (원안에 없는 요건)

다국어 임베딩은 **같은 언어 쌍을 교차 언어 쌍보다 체계적으로 높게** 준다.
한국어로 보정한 값 하나만 쓰면:

| 언어 | 코퍼스 안 top1 | 단일 임계값(0.839) |
|---|---|---|
| ko | 0.893 / 0.866 | 통과 |
| en | 0.800 / 0.843 | 절반 폴백 |
| vi | 0.800 / 0.811 | **전부 폴백** |

다국어 서비스에서 비한국어 경로가 항상 폴백되면 기능 상실이다.
→ `ko:0.839 / en:0.795 / vi:0.790`. 언어를 늘리면 반드시 재보정.

### 13. §4.2 — 요건 매트릭스는 대부분 `unknown` 으로 남는다

은행별 계좌개설 요건의 공식 근거를 확보하지 못했다. **추정으로 채우면 그 자체가
환각**이므로 비워 둔다. 제도 차원에서 확인된 사실(한도, 모바일 등록증 6개 은행)만
`common` 에 `official` 로 넣었다.

기획서가 "8기관 × 12비자 = 96셀"을 목표로 서술했다면, **채운 셀 수가 아니라
3값 상태 관리 자체**를 성과로 서술하는 편이 정직하고 강하다.

### 16. 부록 B3 — 거래목적 확인 의무는 **한도해제에도** 걸린다

기획서는 "계좌 개설 시 거래목적 확인 의무화(2024.8.28)"로만 적혀 있다.
시행령 원문은 대상을 둘로 적는다.

> 고객의 **계좌개설, 거래한도 제한 해제 시** 금융거래 목적 확인

| | |
|---|---|
| 근거 | `corpus/processed/FSC-PURPOSE-ENFORCEMENT-DECREE.md` (금융위, 2024-08-19) |
| 조치 | B3 서술에 "및 한도제한 해제 시" 추가 |

**이건 서술 보강이 아니라 서비스 구조의 근거다.** F2(계좌개설)와 F4(한도해제)가
서로 다른 기능이 아니라 **같은 법 조항의 앞뒤**라는 뜻이고, "왜 서류를 내야
하는가"에 대해 두 기능이 같은 답을 공유한다. 기획서 §4가 두 기능을 병렬로
나열했다면, 하나의 제도에서 갈라진 두 시점으로 다시 쓰는 편이 강하다.
