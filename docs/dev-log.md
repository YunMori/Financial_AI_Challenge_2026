## 2026-08-11 — Phase 0: 리포 정리

### 실측값

- CSV 4종 전부 **CP949** (파일명뿐 아니라 내용도). `file -I`는 `iso-8859-1`로 보고하지만
  실제로는 CP949 — `file`은 한국어 완성형을 구분하지 못하므로 `file` 결과를 믿으면 안 됨.
  `python3 -c "open(p, encoding='cp949').read()"`로 확인하는 게 확실.
- 변환 후 행수: 보이스피싱 11 / 시군구 13,578 / 유학생 18,189 / 체류자격 1,891.
- **B1 확정**: 2026-06 체류외국인 **2,874,278명** — 기획서 값과 정확히 일치.
- **B10 확정**: 2025 보이스피싱 **23,360건 / 12,578억 원** — 기획서 값과 정확히 일치.
- 로컬 환경: Python **3.12.3** / Node **22.20.0** / Docker 있음 / uv·pnpm 없음.
  planner는 Python 3.11을 명시했지만 로컬과 Docker 핀을 3.12로 일치시키는 쪽을 택함
  (Phase 1에서 chromadb·kiwipiepy·onnxruntime·weasyprint 휠 설치를 확인하고,
  하나라도 실패하면 양쪽 다 3.11로 내림).

### 결정과 근거

- **생성 LLM = `claude-sonnet-5`**, 폴백 `claude-opus-5`.
  폴백 방향을 위로 잡은 이유: 폴백은 드물게 발동하므로 그때는 비용보다 성공률이 중요하고,
  별도 용량 풀이라 sonnet 쪽 장애를 실제로 피할 수 있음. haiku로 내리면 장애 상황에서
  답변 품질까지 같이 떨어져 폴백의 의미가 없음.
  단가: sonnet-5 $3/$15 per MTok, **2026-08-31까지 도입가 $2/$10 적용**(현재 해당).
  → ADR-002로 승격 예정 (Phase 4)
- **원본 CP949 CSV는 커밋하지 않음.** 재다운로드 가능하고 sha256으로 동일성 검증이 되므로
  중복 보관할 이유가 없음. `_incoming/`을 gitignore 처리하고 변환 스크립트만 커밋.
- **컬럼명은 한국어 원문 유지.** 근거 기반 서비스에서 원문 충실성이 코드 편의보다 중요.
  의미는 `corpus/stats/SOURCES.md`에 대역표로 남김.
- **통계 CSV는 RAG 코퍼스에 넣지 않음.** `corpus/stats/`와 `corpus/raw/`를 분리.
  이 4종은 배경 수치 근거이지 검색 대상이 아님 — 섞으면 청킹 규칙(§4.4)이 무의미해지고
  검색 결과에 표 조각이 섞여 인용 품질이 떨어짐.

### 기획서와 어긋난 지점 (§0.3 표에 추가 대상)

1. **`LLM_REGION=kr` 충족 불가.** Anthropic API는 해외 리전.
   대신 실제로 참인 서술로 교체: **임베딩·벡터DB·BM25·가드레일·계층 판정은 전부 로컬,
   외부로 나가는 것은 생성 호출 하나뿐.** 문구를 안 고치면 심사에서 그대로 지적당함.
2. **"체류외국인"과 "등록외국인" 혼용 위험.** 같은 2026-06 시점에
   체류외국인 2,874,278 vs 등록외국인 1,636,922 — 90일 초과 등록자만 후자에 잡힘.
   외국인등록증이 계좌개설의 전제이므로 **서비스 실질 모수는 등록외국인(163만)** 쪽.
   기획서 §3장에서 287만을 서비스 대상 규모로 쓰고 있다면 과대 서술임.
3. **보이스피싱 통계 범위.** 확보한 경찰청 자료는 기관사칭형·대출사기형 **2종만** 집계.
   "보이스피싱 전체"로 서술하려면 유형 범위를 각주로 밝혀야 함.
4. **F1 체류자격 12종에서 F3(동반) 84,976명 누락.** E-7(87,097)과 맞먹는 규모이고,
   취업·유학 체류자의 배우자·자녀로 장기체류하며 계좌가 실제로 필요한 집단.
   12종 자체는 체류외국인의 68.7%를 덮고 빠진 상위는 전부 단기체류(B2·C3·B1)라
   선정은 타당하지만, F3는 코퍼스 여력이 생기면 우선 확장 후보.

### 막힌 지점

- **공공데이터포털 데이터셋 URL 4건 미확보.** 파일은 있는데 출처 URL이 없음.

### 결정과 근거

- **`app/rag/tokenize.py`를 Phase 3이 아니라 지금 작성.** 아래 정규식 버그를
  발견한 시점에 검증된 형태를 손에 쥐고 있었고, 의존성 없는 잎 모듈이라

- **`SessionContext`의 모든 필드를 선택 사항으로.** 프로필 없이도 일반 안내가

  메타데이터 필터만 해제된다.
- **히스토리 초과는 거절이 아니라 절삭.** 클라이언트 버그로 히스토리가
  길어졌다는 이유로 이용자의 질문을 실패시킬 이유가 없음.

### 기획서와 어긋난 지점

5. **★ planner §6.3의 `VISA_RE` 정규식이 실제로 작동하지 않음.**

   원안: `re.compile(r"\b([A-H]-\d{1,2})\b")`

   뒤쪽 `\b`는 숫자 다음에 **한글이 오면 경계가 성립하지 않는다**(한글도
   Python의 `\w`에 포함되므로). 그래서 가장 자연스러운 한국어 어순에서 실패:

   | 입력 | 원안 | 수정본 |
   |---|---|---|
   | `E-9 비자입니다` | `['E9']` | `['E9']` |
   | `E-9인데요` | **`[]`** | `['E9']` |
   | `E-7과 E-9의 차이` | **`[]`** | `['E7','E9']` |
   | `E9 비자 계좌개설` | **`[]`** | `['E9']` |
   | `제가 D-2에요` | **`[]`** | `['D2']` |
   | `e-9 소지자` | **`[]`** | `['E9']` |

   **E-9/E-7 혼동 방지는 이 서비스 검색 설계의 핵심 주장인데, 원안대로면
   그 주장이 성립하지 않는다.** 기획서 §8.3에서 "BM25는 E-9와 E-7을 완전히
   다른 토큰으로 취급한다"고 서술한 부분의 근거가 무너짐.

   수정: `r"(?<![A-Za-z0-9])([A-H]-?\d{1,2})(?![0-9])"` + `IGNORECASE`
   - 앞쪽 부정후방탐색 — "TYPE-9"의 E를 잡지 않음 (검증됨)
   - `-?` — `E-9`와 `E9` 둘 다 허용
   - 뒤쪽 `(?![0-9])` — `D-10`을 `D-1`로 잘라 읽지 않음

   회귀 방지 케이스 17개를 `tests/test_tokenize.py`에 고정.

6. **복합명사 분해 확인됨(원안이 옳았음).** 사용자 사전 없이 kiwi 기본 사전은
   `한도제한계좌` → `한도/제한/계좌`로 쪼갠다. 쪼개지면 "한도 제한 있는 계좌"류
   무관 문서까지 매칭되어 변별력이 사라짐. 도메인 용어 24종을 NNP로 등록.
   **이 사실 자체를 테스트로 고정**(`test_split_would_lose_discrimination`) —
   나중에 kiwi가 기본 사전을 개선하면 사용자 사전 항목을 재검토해야 하므로.

### 막힌 지점

- **starlette 1.6.0의 `TestClient`가 httpx2를 권고**(현재는 deprecation 경고).
  테스트는 통과하지만 다음 메이저에서 깨질 수 있음. anthropic이 httpx에

## 2026-08-12 — Phase 2: 코퍼스 파이프라인

### 실측값

- P0 문서 **9건 수집·정제 완료** → **30청크** (평균 711자, 최대 1,550자).
  금융위 보도자료 2종(HTML+PDF), 정책브리핑 2종, 하이코리아 3종.
- 임베딩 `intfloat/multilingual-e5-large` (1024차원). 모델 로드 61초 /
  30청크 임베딩 26초. BM25 평균 145토큰.
- 검색 스모크 테스트 3건 전부 정답 문서를 상위에 회수 (dense·BM25 양쪽).

### 결정과 근거

- **fastembed 는 BGE-m3 를 지원하지 않는다.** 다국어 옵션은
  `multilingual-e5-large`(2.24GB) / `mpnet`(1.0GB) / `MiniLM`(0.22GB) 뿐.
  BGE-m3·KURE 를 쓰려면 `sentence-transformers`(torch) 가 필요하고 이는
  Render 메모리 예산에 직접 영향을 준다.
  → 지금 확정하지 않고 `app/rag/embed.py` 에 **백엔드 추상화**를 두었다
  (`EMBED_BACKEND=fastembed|sentence_transformers`). M1 은 e5-large 로 진행하고,
  Phase 7 컨테이너 실측 후 ADR-003 으로 확정한다.
- **e5 계열은 `query:` / `passage:` 접두어가 필수다.** 붙이지 않으면 성능이
  크게 떨어지는데 에러가 나지 않아 알아채기 어렵다. `embed.py` 가 모델명에
  "e5" 가 있으면 자동으로 붙인다. BGE 계열은 접두어를 쓰지 않으므로 백엔드
  교체 시 이 분기가 그대로 맞아야 한다.
- **통계 CSV 는 청킹 대상이 아니다** — `corpus/stats/` 와 `corpus/raw/` 분리 유지.
- **매트릭스 4셀을 전부 `unknown` 으로 두었다.** 은행별 계좌개설 요건의 공식
  근거를 확보하지 못했기 때문이며, 추정으로 채우면 그 자체가 환각이 된다.
  대신 제도 차원에서 확인된 사실(한도, 모바일 등록증 6개 은행)은 `common` 에
  `official` 로 넣었다. 3값 UI 를 검증할 표본이 필요하므로 **일부러 남겨 둔다.**

### 기획서와 어긋난 지점

7. **★ 부록 B2 의 "1일 한도 100만 원"이 부정확하다.** 금융위 보도자료 원문 확인:
   **인터넷뱅킹 100만 · ATM 100만 · 창구 300만 원**(상향 전 30/30/100).
   거래유형을 명시하지 않으면 심사에서 지적당한다. 데모 시나리오 2는 전자금융
   이체 맥락이라 100만 원이 맞으므로 시나리오 자체는 유효하다.
   추가 확인: **은행별 시행일 차이** — 농협·하나·부산은행은 2024-05-10.

8. **B7 은 정확했다** (2025-03-21, 6개 은행). 은행 명단까지 확보:
   신한·하나·아이엠뱅크·부산·전북·제주, 이 중 신한·전북은 비대면 가능.
   단 **발급 개시일(2025-01-10, 법무부)과 금융 이용 개시일(2025-03-21)이 다르다** —
   혼동하면 안 된다.

### 막힌 지점과 해결

- **PDF 가 `.html` 로 저장되는 버그.** 정부 첨부파일 URL 은
  `/comm/getFile?srvcId=…` 형태라 확장자가 없다. URL 접미사로 판단하면 파서가
  잘못 선택된다. → `sniff_ext()` 로 매직 바이트(`%PDF-`, `PK\x03\x04`, OLE) 판별.

- **★ 바이트 해시로 변경을 감지하면 HTML 이 매번 "바뀜"으로 뜬다.**
  정부 포털은 조회수 카운터와 세션 토큰이 매 요청 달라진다(실제 diff 로 확인).
  **항상 울리는 경보는 무시하게 되고, 정작 내용이 바뀐 날 놓친다** — §8.4 의
  오염 방어가 무력해지는 실패 모드다.
  → 바이트 해시는 **출처 기록용**으로만 쓰고, 실질 변경 판정은 02_clean 이
  **추출 텍스트 해시(`text_sha256`)** 로 한다. 적용 후 오탐이 사라졌다.

- **하이코리아는 탭마다 별도 페이지(`CAT_SEQ`)다.** 상위 페이지를 수집하면
  제목은 "외국인등록 안내"인데 본문은 엉뚱한 "변경신고"인 문서가 만들어진다.
  그대로 두면 **검색이 없는 내용을 하이코리아 출처로 인용**하게 된다 —
  서비스가 막으려는 실패 그 자체. → 필요한 탭을 doc 단위로 지정.
  `체류자격별 안내매뉴얼`(CAT_SEQ=5400)은 링크 목록뿐이라 THIN 으로 걸러 제외.

- **표가 조각나는 문제.** trafilatura 는 표 행을 파이프로 시작하지 않게 내보내고
  (`A | B |`), 셀이 길면 **파이프가 아예 없는 줄로 감는다**. 줄 단위 정규식으로는
  그 지점에서 표가 끊기고, 특정 체류자격 행만 검색되어 다른 자격의 요건으로
  오독될 수 있다. → 상태 기반 감지 + 산문 3줄 허용치.
  결과: 체류자격 제출서류 표 **28종이 한 청크에 유지**된다.

- **검색 임계값 재보정 필요.** e5 의 코사인 점수는 0.87~0.90 대에 몰린다
  (설정의 `threshold_top1=0.42` 는 다른 척도 기준). 골든셋이 생기면
  이 분포로 다시 잡아야 한다 — 지금 값으로는 폴백이 전혀 걸리지 않는다.

- **`User-Agent` 에 한글을 넣어 `UnicodeEncodeError`.** HTTP 헤더는 ASCII 만
  허용된다. → 영문으로 교체.

- **은행연합회(kfb.or.kr) SSL 핸드셰이크 실패**(`SSLV3_ALERT_HANDSHAKE_FAILURE`).
  구형 TLS 설정. `legacy_tls: true` 옵션을 만들어 두었으나 **인증서 검증은
  유지**한다(검증까지 끄면 중간자 공격에 코퍼스가 열린다). M1 소스에는 미사용.

### 결정과 근거

- **planner 원안의 `threshold_top1=0.42`는 e5 척도에서 무의미하다.**
  코사인 유사도가 0.76~0.91에 몰려 있어 0.42로는 폴백이 **한 번도** 걸리지
  않는다. 검색 신뢰도 임계값 전체가 죽어 있던 셈. → 0.839로 교체하고,
  값을 되돌리면 실패하는 테스트(`test_threshold_matches_measured_distribution`)를
  걸어 두었다.

- **★ RRF margin은 신뢰도 신호로 쓸 수 없다 — 비활성화(0.0).**
  실측에서 코퍼스 *밖* 질의가 오히려 높은 margin을 냈다(0.0167 vs 0.0005).
  원인: RRF margin은 "두 검색기가 같은 문서를 골랐는가"를 재는 값이지
  "근거가 존재하는가"와 무관하다. 무관한 질의라도 dense·BM25가 우연히
  같은 문서를 1위로 뽑으면 margin이 커진다.
  planner §6.6의 `threshold_margin=0.05`를 그대로 뒀다면 **모든 질의가
  폴백**됐을 것이다(실측 margin 최대 0.017). 대체 신호는 골든셋과 함께 설계.

- **`verified_at` 이 비면 STALE로 취급한다.** 모르는 것을 최신으로 취급하면
  시점 경고의 의미가 없다. 다만 그 결과 초기에는 **모든 문서가 STALE**로 떠
  경고가 상시 켜져 있었다 — 경보가 항상 울리면 무시된다는 Phase 2의 교훈과
  같은 구조. → P0 9건의 정제본 내용을 확인하고 `verified_at=2026-08-12`,
  `verified_method` 를 manifest에 기록. 이후 STALE 0/5로 정상화.

- **모델명의 단일 출처를 `Settings.embed_model` 로 통일.** `config.py`는
  bge-m3, `embed.py`는 e5-large를 기본값으로 두고 있어 색인기와 런타임이
  다른 모델을 볼 뻔했다. 인덱스에 기록해 둔 모델명과 대조하는 경고가
  이걸 잡았다(`04_index` 가 `embed_model` 을 pickle에 저장 → `retrieve` 가 대조).
  **벡터 공간이 어긋나면 에러 없이 검색만 조용히 무너진다.**

- **체류자격 필터는 후보 3건 미만이면 해제한다**(과필터 방지). 근거를 못 찾아
  폴백하는 것보다 넓게 찾고 계층 판정에 맡기는 편이 낫다.

- **BM25 점수 0인 후보는 순위를 주지 않는다.** 매칭이 하나도 없다는 뜻인데
  순위를 주면 RRF가 무관한 문서를 끌어올린다.

  (`test_check_order_number_before_forbidden`).
- **폴백 사유를 이용자에게 노출하지 않는다.** `unsupported_number` 를 보여주면

  로그·지표에만 쓰고 화면에는 `low_confidence` 와 같은 문구를 낸다.
  테스트로 고정(`test_internal_reasons_are_not_exposed`).
- **폴백에도 근거를 표시한다.** 답을 못 주더라도 "무엇을 봤는지"는 보여주는 편이
  이용자가 스스로 판단하는 데 도움이 된다.
- **`numeral_supported` 는 파싱 실패를 "지지됨"으로 본다.** 서류명이
  `numbers_used` 에 섞여 들어온 것을 근거 부족으로 오판하면 정상 답변이
  차단된다 — 여기서는 거짓 폴백을 늘리는 쪽이 더 나쁘다.

### 막힌 지점과 해결

- **★ 같은 정규식 버그를 세 번째로 만났다.** 뒤쪽 `\b` / `(?![\w])` 가
  한국어 조사 앞에서 경계를 만들지 못한다.

  | 발견 시점 | 대상 | 놓친 입력 |
  |---|---|---|
  | Phase 1 | 체류자격 `VISA_RE` | `E-9인데요`, `E-7과 E-9의` |
  | Phase 4 | 수량 `QUANTITY_RE` | `100만원입니다`, `30만원에서` |
  | Phase 4 | PII `resident_id` 등 | `900101-1234567입니다` |

  **한국어 텍스트에 `\b` 계열 경계를 쓰면 안 된다**는 것이 이 프로젝트의 규칙이
  되어야 한다. 앞쪽만 부정후방탐색으로 막고 뒤는 열어 둔다.

- **★ 인젝션 패턴이 핵심 정상 질의를 오탐했다.**
  `(규칙|제한|가드레일).{0,8}(해제|무시|우회|없이)` 가 **"한도제한계좌 해제"** 에
  걸린다. 이 서비스에서 가장 자주 들어올 질문이 필터되는 것이다.
  → `제한` 을 패턴에서 제거. 인젝션 탐지는 오탐 비용이 크므로 좁게 잡고,
  구조적 분리(role 분리, `<context>` 격리)를 1차 방어로 둔다.
  회귀 방지: 정상 질의 3종이 `injection_hits == 0` 인지 확인.

- **증분 JSON 파서가 깨진 유니코드에서 다음 이스케이프를 삼켰다.**
  `\uXXXX` 를 길이만 보고 자르면 `\ud5` 뒤의 `글` 에서 백슬래시까지
  먹어 남은 본문이 화면에 그대로 샜다. → 16진수만 소비하도록 수정.

- **널 바이트가 소스에 섞였다.** 패치 스크립트에서 `_MASK = " "` 리터럴에
  NUL 이 들어가 `SyntaxError: source code string cannot contain null bytes`.
  제거 후 빈 문자열이 되면 슬라이스가 **삭제**되어 인덱스가 밀리는 2차 버그가
  생기므로, 길이를 보존하는 공백으로 되돌렸다.

### 남은 위험

- **키 미확보로 실제 생성 경로가 한 번도 실행되지 않았다.** 규칙 기반 부분
  (계층 판정·가드레일·숫자 대조·스트리밍 파서)은 전부 검증됐으나,
  Anthropic 호출·구조화 출력 파싱·캐시 적중·거절 처리는 미검증이다.
  `NullLLMClient` 로 파이프라인이 죽지 않는 것만 확인했다.

### ★ 발견 1 — 작은 임베딩 모델은 품질이 아니라 안전장치를 없앤다

| 모델 | RSS | 코퍼스 안 최소 | 밖 최대 | 분리 |
|---|---:|---:|---:|---:|
| e5-large | 1,510 MiB | 0.8494 | 0.8293 | **+0.0200** |
| MiniLM | 820 MiB | 0.4099 | 0.6841 | **−0.2742** |
| mpnet | 1,987 MiB | — | — | (측정 안 함) |

MiniLM 에서는 **코퍼스 밖 질의가 안쪽보다 높은 점수를 받는다.** `low_confidence`
폴백 판정이 원리적으로 불가능해지고, "근거가 없으면 답하지 않는다"는 핵심
주장 하나가 사라진다. 메모리와 맞바꿀 수 있는 것이 아니다.

mpnet 은 e5-large 보다 메모리가 크고(+477 MiB) 로드가 10배 느려(40.5s) 제외.

### ★ 발견 2 — 한국어로 보정한 임계값이 비한국어 질의를 전부 거부했다

|---|---|---|
| ko | 0.893 / 0.866 | 통과 |
| en | 0.800 / 0.843 | 절반 폴백 |

성립하지 않는다. → 언어별 임계값(`ko:0.839 / en:0.795 / vi:0.790`) 도입.
세 언어 모두 안/밖 분리 확인. 회귀 테스트 3개 추가.

> 질의 정규화(③)가 한국어 검색어를 만들면 격차가 줄지만, 사전 히트만으로
> 끝나는 경우가 있어 안전망이 필요하다. **API 키가 없는 지금은 정규화가
> 사실상 동작하지 않으므로 이 임계값이 다국어 경로를 지탱하고 있다.**

### 막힌 지점과 해결

- **★ 컨테이너에서만 터지는 기동 실패.** `REPO_ROOT = parents[3]` 가 Docker 에서
  `IndexError` 를 낸다 — 이미지에는 `/app/app/config.py` 만 있어 부모가 3개뿐이다.
  로컬 테스트 263개가 전부 통과하는데 **컨테이너는 기동조차 못 했다.**
  planner §15.4 가 경고한 "로컬에선 됐는데" 사고의 정확한 사례.
  → 표식(`corpus/`, `.git`)으로 찾도록 변경. 용어사전 경로도 같은 원인이었다.

- **Docker 빌드 컨텍스트가 `apps/api` 면 `corpus/glossary` 를 담을 수 없다.**
  → 컨텍스트를 리포 루트로 올리고 `.dockerignore` 로 불필요한 것을 제외.

  기다린다. 심사위원이 처음 접속했을 때 그 일이 벌어진다. → `RUN python -c ...`
  로 이미지에 캐시.

- **검증 스크립트 오류 2건** (코드 문제 아님):

  "순수 인젝션 → 중화" 기대는 잘못이었다 — 실질 질문이 없는 100% 인젝션은
  차단이 옳다. 검증 항목을 "인젝션+질문 → 중화" / "순수 인젝션 → 차단" 둘로 분리.

### HWP 추출기를 넣었다

국내 정부 보도자료의 1차 첨부는 HWP 다. HWP 5.0 은 OLE 복합문서이고
BodyText 가 raw deflate 로 압축된 레코드 열이다. 표는 셀마다

구현하면서 만난 것:

- **셀을 순서대로 이으면 안 된다.** 병합이 있는 표에서 값이 한 칸씩 밀려
  다른 행의 숫자를 읽는다. 좌표에 배치해야 한다.
- **셀의 LIST_HEADER 는 표 레코드와 같은 레벨**이다. `lvl > level` 로 두면

### ★★ 숫자 대조가 한국어 표기만 알고 있었다 — 다국어 서비스인데

새로 넣은 계측(`unsupported_numbers` 기록)이 바로 답을 줬다. 거부된 값들:

```
['3.000.000 won']   ['30 million won', '300 million won']   ['100,000 KRW']
['2012년']  ['2024-05-10']  ['2025년 10월']
```

날짜 쪽은 파서가 정상이었다(`2012년`·`2024-05-10` 모두 근거에 있으면 통과).
**금액 쪽이 깨져 있었다.**

| 표기 | 파싱 결과(수정 전) | 실제 값 |
|---|---:|---:|
| `3.000.000 won` (베트남어) | **3** | 3,000,000 |
| `30 million won` | **30** | 30,000,000 |

베트남어·유럽식 천단위 점을 **소수점으로 읽고 있었다.** `3.000.000` →
`\d[\d,]*(?:\.\d+)?` 가 `3.000` 을 먹고 3.0 으로 만든 뒤 나머지를 흘린다.
**1,000,000 배 틀린 값**이다. 방향이 양쪽으로 위험하다 — 근거에 `3` 이 있으면
틀린 금액이 통과하고, 없으면 정상 답변이 차단된다.

답변은 ko/en/vi 로 나가는데 파서는 `100만원` 형태만 이해하고 있었다.
**"가장 실용적인 환각 방어"가 세 언어 중 둘에서 제대로 동작하지 않았다.**

→ 천단위 점 표기(`3.000.000`)와 영어·베트남어 배수어(million/triệu/nghìn),
베트남 동(vnd) 단위를 추가했다. 소수점(`3.5`, `2.5%`)은 깨지지 않도록
"1~3자리 + (점+정확히 3자리)⁺" 형태일 때만 구분자로 본다. 회귀 테스트 9종 추가.

### 다국어 금액 수정 후 (`exp_004`) — 남은 것은 전부 날짜였다

금액 표기 수정으로 `3.000.000 won` · `30 million won` · `100,000 KRW` 가
거부 목록에서 **사라졌다.** 남은 `unsupported_number` 는 전부 날짜다:

```
['2012년']  ['2016년']  ['2024년 5월 2일']  ['2024년 5월 10일']  ['29/3/2024']
```

두 갈래로 갈렸다.

1. **`29/3/2024` 는 파서 결함이었다.** 연도가 뒤에 오는 표기(베트남·유럽)를
   날짜로 못 읽고 **수 29** 로 읽었다. 천단위 점과 같은 부류다.
   일/월 순서가 모호한 경우(`5/3/2024`)는 한쪽으로 찍지 않고 **가능한 해석을
   모두 대조**하도록 했다 — 찍으면 절반이 틀린다.

2. **`2012년` 은 파서가 옳았다.** `2012` 는 코퍼스 71청크에 **한 번도 나오지
   않는다.** 모델이 지어낸 연도이고, 숫자 대조가 정확히 잡은 것이다.

### 골든셋 160문항 확장 (`exp_005`) — 그리고 가장 중요한 발견

en 2건 / vi 1건뿐이라 두 언어 임계값이 신뢰 구간 없이 잡혀 있었다 →
en 10 / vi 10 으로. 확장분 60건 중 19건을 여기에 썼다.

| 지표 | 100문항 (exp_004) | 160문항 (exp_005) |
|---|---:|---:|
| Recall@5 | 93.8% | **94.6%** |
| 인용률 | 100% | 100% |
| 숫자 정확도 | 100% | 100% |
| 사실 포함률 | 88.9% | **93.1%** |
| **`low_confidence` 과잉폴백** | 3건 | **3건 = 3.3%** ✅ |
| 과잉폴백 (총량) | 21.5% | 20.7% ★ |

**게이트 자체는 목표에 들어왔다** — `low_confidence` 과잉폴백 3.3% (목표 ≤8%).
총량 20.7% 중 13건은 `unsupported_number`, 즉 환각을 막은 것이다.

### ★★★ 계층 C 규칙이 베트남어에는 아예 없었다

exp_005 에서 새어 나간 함정 5건 중 **3건이 vi, 그것도 계층 A** 였다.
계층 A 는 "공식 근거로 확인된 사실"이라는 뜻이다. 즉 **확신을 갖고 답했다.**

| 질문 | 언어 | 결과 |
|---|---|---|
| "Ngân hàng nào tốt nhất cho người nước ngoài?" (어느 은행이 제일 좋나요) | vi | **계층 A** |
| "Tôi nên chọn ngân hàng nào?" (어느 은행을 골라야 하나요) | vi | **계층 A** |
| "tin nhắn nói tài khoản bị khóa, có thật không?" (이 문자 진짜인가요) | vi | **계층 A** |
| "I got a text saying my account is frozen — is it real?" | en | **계층 A** |

`rules.py` 를 열어 보니 패턴이 **한국어와 영어뿐**이었다. 주석은 "그 외 언어는
정규화 후 한국어 검색어에 대해 다시 호출한다(2차 방어)"라고 적혀 있었는데,
**정규화는 검색어를 만드는 것이지 의도를 보존하지 않는다.** "어느 은행이 제일
좋나요"가 "은행 선택" 같은 검색어가 되면 계층 C 패턴에 걸리지 않는다.

영어 쪽도 구멍이 있었다. 사기 판정 패턴이 `scam|phishing|fraud` 라는 **단어를
요구**한다. 그런데 이용자는 "사기인가요"가 아니라 **"진짜인가요"** 라고 묻는다.

**이 서비스의 주 이용자는 비한국어 화자다.** 은행 추천과 사기 판정은 이 서비스가
존재하는 이유에 해당하는 거절 대상인데, 그 거절이 주 이용자 언어에서 동작하지
않고 있었다. 골든셋을 15 → 41문항으로 늘리지 않았으면 드러나지 않았을 것이다.

→ 베트남어 패턴 7종 신설, 영어 사기·추천 패턴 확장.

**오탐을 실측으로 걸러냈다.** 처음 넣은 `(có được|có thể) … không` 이
`"Có thể dùng thẻ cư trú điện tử để mở tài khoản không?"`(모바일 등록증으로
계좌를 열 수 있나요)를 막았다. `có thể … không` 은 베트남어의 **일반 의문문
형태**라 문형으로 잡으면 정상 질문이 통째로 막힌다. 개별 심사 요구의 표지는
문형이 아니라 **1인칭 주어**다. → 해당 패턴 삭제.
한국어 인젝션에서 `제한` 을 뺐던 것과 같은 판단이다.

결과 (골든셋 160문항 정규식 단독):

| | 수정 전 | 수정 후 |
|---|---:|---:|
| 정상 문항 오탐 | 0/92 | **0/92** |
| vi 함정 포착 | **0/10** | **8/10** |
| en 함정 포착 | 4/10 | 6/10 |

### ★ 지연 — 설정으로 줄일 수 있는 것이 아니었다

`thinking` 과 `effort` 를 지연 예산의 손잡이로 보고 조합을 실측했다
(ko 30문항, 다른 작업을 모두 멈추고).

| 설정 | 출력 토큰/건 | p50 | p95 |
|---|---:|---:|---:|
| adaptive + medium (현행) | 525 | 7,250ms | 13,258ms |
| adaptive + **low** | **405** (−23%) | 7,409ms | **10,880ms** |

**출력 토큰을 23% 줄였는데 p50 은 움직이지 않았다.** p95 만 2.4초 내려갔다.
즉 지연은 사고량에도 출력 길이에도 비례하지 않는다 — **요청당 고정
오버헤드(약 5~6초)가 지배**하고 있고, 그건 설정으로 건드릴 수 없다.
효력을 낮추면 p95(꼬리)는 나아지지만 중앙값은 그대로다.

정규화 호출(③)은 이미 haiku-4-5 · `max_tokens=128` 이라 손댈 것이 없었다.

> 첫 시도는 **오염된 측정**이었다. `exp_006` 채점이 백그라운드로 같은 API 를
> 두드리는 동안 재서 값이 비단조로 나왔다(효력을 낮췄는데 p50 이 올라감).
> 지연을 잴 때는 다른 부하를 전부 멈춰야 한다 — 이 프로젝트에서 CPU 경합으로
> 리랭커 지연을 잘못 잴 뻔한 것과 같은 실수다.

### ★ 그래서 지금까지 **틀린 것을 재고 있었다** — TTFT 를 넣었다

planner §14.2 는 "체감 지연 관리 — TTFT를 별도 지표로"라고 명시해 뒀다.
그런데 하니스는 TTFT 를 **한 번도 재지 않았고**, `latency_ms` 는 최종 이벤트까지의
총 완료 시간이다. 스트리밍 서비스에서 이용자가 느끼는 것은 화면에 첫 글자가
뜨기까지의 시간이지 답변이 끝나는 시간이 아니다.

총 완료 시간이 고정 오버헤드에 묶여 있다면, 그 숫자를 6초로 내리는 것은
설정 튜닝의 문제가 아니다. 반면 TTFT 는 스트리밍이 살아 있는 한 짧고,
그것이 planner 가 애초에 관리하라고 한 값이다.
→ `Outcome.ttft_ms` 추가, 첫 `token` 이벤트까지를 재서 리포트에 남긴다.

**P95 6초 목표를 "총 완료 시간"으로 유지할지, planner §14.2 대로 TTFT 로
옮길지는 기획 판단이 필요하다.** 측정 장치는 이제 양쪽 다 있다.

### 계정 크레딧 소진 — llm 모드 측정이 여기서 멈췄다

`exp_006` 재실행 도중 API 크레딧이 바닥났다.

```
400 invalid_request_error: Your credit balance is too low to access the
Anthropic API. Please go to Plans & Billing to upgrade or purchase credits.
```

19건까지 생성한 뒤 나머지가 전부 `upstream_error` 폴백으로 떨어져
과잉폴백이 79.3% 로 찍혔다 — **코드 결함이 아니라 잔액 문제다.**
그 실행의 지표는 전부 무효다. 크레딧을 채우기 전까지 llm 모드 채점은 불가능하다.

> 이 하루에 exp_002~006 + 리랭커 실험 + 지연 실험을 돌렸다. 골든셋 160문항
> 1회가 약 47만 입력 · 5.3만 출력 토큰이므로, 실험 계획을 세울 때 **회당 비용을
> 먼저 계산**하는 절차가 필요하다. 캐시 적중률이 97~99% 라 입력 쪽은 이미
> 최적이고, 남은 변수는 실행 횟수다.

### `exp_006` 리포트 파일이 없다 (측정은 유효, 산출물만 유실)

계층 C 다국어 수정의 효과는 **측정됐고 로그에 남아 있다** — 폴백 정확도
92.6% → **98.5%**(67/68), 폴백 사유 일치 66.2% → **83.8%**, 인용 100%,
Recall@5 94.6%, 숫자 100%, 금지표현 0.

다만 리포트 JSON 은 쓰이지 못했다. 내가 넣은 과잉폴백 사유 출력 블록이
`print_report()` 의 지역 변수 `m` 을 `main()` 에서 참조해 **채점이 다 끝난 뒤
파일 쓰기 직전에** `NameError` 로 죽었다. 두 번째 시도는 위 크레딧 문제로 무효.
→ 버그는 고쳤고(`ttft_ms` 가 `value` 키 없이 표 출력에 끼어 터지던 것도 함께),
크레딧이 복구되면 `exp_006` 을 재생성해야 한다. **커밋된 정량 증거는
`exp_001`~`exp_005` 까지다.**

### ✅ 다국어 PDF 조판 선행 검증 통과 (planner §12.1)

planner 가 5주 차 선행 검증으로 못박은 리스크를 컨테이너에서 확인했다.
**5GB 앱 이미지를 다시 만들지 않고**, `apps/api/Dockerfile` 과 같은 조판
의존성·폰트만 뽑은 최소 이미지로 조판 질문만 격리해 답했다.

| 검사 | 결과 |
|---|---|
| 텍스트 왕복 ko/en/vi | OK |
| 한글 폰트 선택 | `Noto-Sans-CJK-KR` |
| 베트남어 확장 글자 폰트 | `Noto-Sans` |
| **베트남어 성조 결합문자** | **합자 정상** — 결합기호가 별도 글자로 찍히지 않음 |
| 폰트·글리프 경고 | 0건 |

`ảạếị—ấờứệ` 가 각각 한 글자로 찍혔다. planner §12.2 가 "확인 필수"로 적은
항목이고, 여기서 실패하면 조판은 성공하는데 글자만 깨진다.

**검증 방법을 텍스트 비교로만 하면 안 된다.** 두부(tofu)로 찍혀도 코드포인트는
그대로 추출되므로 통과해 버린다. `pdfplumber` 로 **글자별 폰트명**을 뽑아
한글이 CJK 폰트에, 베트남어가 라틴 폰트에 각각 걸렸는지 대조했다.

### 기획서 단순화 근거 — @font-face unicode-range 가 불필요하다

planner §12.2 는 `@font-face` + `unicode-range` 로 스크립트별 폰트를 손수
지정하는 CSS 를 제시했다. 실측에서는 `font-family: "Noto Sans", "Noto Sans
CJK KR"` 만으로 fontconfig 가 글자마다 올바른 폰트를 골랐다 —
폰트 파일을 리포에 넣고 경로를 관리할 이유가 없다.

공개 언어가 ko/en/vi 3종으로 확정됐으므로(R2 컨티전시) 태국어·중국어·
키릴 서브셋 항목도 현재는 불필요하다. **필요해지면 그때 넣는다.**

### 2026-08-12 (M3) — 로컬 모델 전환 착수, 그리고 숨어 있던 전제들

API 크레딧 소진을 계기로 **생성을 로컬 모델로 내리기로** 했다. 다만 근거는
비용이 아니다(160문항 1회 $1.59). ADR-002 가 "감수하는 것"으로 적은 **국내
리전 원칙 미충족**을 AWS 서울 리전 + 로컬 생성으로 실제 해소하는 것이 목적이다.

`LLMClient` 가 이미 Protocol 이라 **파이프라인 본문을 한 줄도 고치지 않고**
백엔드를 꽂았다. planner §2.3 이 "교체 비용 0"을 노리고 경계를 먼저 그어 둔
것이 여기서 값을 했다.

#### ★★ 선택 필드는 문법이 생략을 허용한다 — 안전장치가 조용히 꺼졌다

가장 중요한 발견이다. `LLMAnswer.citations` 는 `default_factory=list` 라 JSON
스키마의 `required` 에 들어가지 않는다. XGrammar 는 그걸 그대로 반영해 **생략을
허용**하고, Qwen3-4B 는 `answer`·`tier`·`numbers_used` 를 채운 뒤
**`citations` 를 통째로 건너뛰었다.** 인용 0건 → 후처리 차단 → 정상 답변이
`no_citation` 폴백.

**Anthropic 경로가 멀쩡했던 것은 Claude 가 지시를 따라 채웠기 때문이지 스키마가
강제해서가 아니다.** 모델의 선의에 기대고 있던 자리였고, 모델을 바꾸자 드러났다.
→ 문법 컴파일 직전에만 모든 속성을 `required` 로 만든다. Pydantic 모델은
그대로 둔다(입력 관용은 유지, 생성 문법만 엄격).

#### ★ `answer` 를 첫 필드에 둔 설계가 길이와 충돌한다

`answer` 가 스키마 첫 필드인 것은 스트리밍 TTFT 를 위한 의도적 설계다. 그런데
본문이 길면 `max_new_tokens` 를 소진해 **뒤따르는 `citations`·`numbers_used` 가
생성되기 전에 잘린다** — 역시 `no_citation`. **길이가 곧 차단 사유가 되는
구조**다. 1024 → 2048 로 올리고 프롬프트에 3~5문장·400자를 명시했다.
"짧게"라는 지시만으로는 소형 모델이 길게 쓴다.

#### ★ 프롬프트의 예시가 지시로 읽혔다

`체류자격 코드(E-9 등)가 있으면 포함하세요` — Claude 는 `E-9` 를 **예시**로
이해했지만 Qwen3-4B 는 **지시**로 받아 질문에 없는 E-9 를 모든 검색어에 주입했다.
이 서비스의 핵심 주장이 E-9/E-7 변별인데 모든 질의에 E-9 가 붙으면 BM25 가
오염된다. 예시를 지우고 금지를 명시해 vi Recall@5 를 81.0% → **90.5%** 로 올렸다.

**모델이 관대해서 통과하던 모호함이지 프롬프트가 옳았던 것이 아니다.**

#### 가설이 측정에 부정된 것 — 용어표 주입

코퍼스 표준 용어 35개를 프롬프트에 넣으면 어휘가 수렴할 것으로 봤다. 개별
검색어는 실제로 정확해졌다("한도제한계좌", "외국인등록증 반환"). 그런데
Recall@5 가 **떨어졌다** — en 86.4%→59.1%, vi 81.0%→76.2%. 검색어가 짧고
좁아져 dense 정보량과 BM25 후보 폭이 함께 줄었다.
**용어가 정확한 것과 검색이 잘 되는 것은 다른 문제였다.** 되돌렸다.

#### 실측값

| | API | 로컬 Qwen3-4B (mps) |
|---|---:|---:|
| Recall@5 en | 95.5% | 86.4% ★ |
| Recall@5 vi | 95.2% | 90.5% ★ |
| 생성 속도 | — | **11.4 tok/s** (문법 없이도) |
| 총 지연 (ko, 근거 5건) | 6.3s | **125.0s** |
| TTFT | — | 41.7s |
| 계층 C 함정 차단 | 0ms | **0ms** (규칙이 LLM 이전) |

**골든셋 160문항 전량 채점이 MPS 에서 4~6시간이라 사실상 불가능하다.** 계획한
결정 게이트를 로컬에서 실행할 수 없다 — AWS GPU 가 있어야 판정된다.
XGrammar 는 병목이 아니다(문법 없이도 11.4 tok/s).

#### 같은 함정을 내가 두 번 밟았다

`test_translate_raises` 가 "구현 안 됨"을 보다가 구현 후 **모델이 없어서**
통과하는 상태가 된 것을 고쳤는데, 같은 파일의 `test_generation_not_
implemented_yet` 에서 똑같은 짓을 반복했다(CPU 로 4B 를 올리려다 실패해서 통과).
둘 다 로드를 가짜로 실패시켜 경로만 보도록 바꿨다.
**통과 이유가 바뀐 테스트는 테스트가 아니다.**

### 남은 문제 (리랭킹과 무관하다)

- **지연이 예산을 넘는다.** p50 6,184ms / p95 17,761ms vs 목표 6,000ms.
  `thinking: adaptive` + `effort: medium` 이 유력한 원인이고, 다국어 경로는
  번역 호출이 직렬로 하나 더 붙는다. **단 이 측정은 리랭커 실험과 동시에
  돌아 CPU 경합이 있었으므로 단독 재측정이 필요하다.**
- **숫자 대조가 정상 답변을 막는다.** 과잉폴백 22건 중 **12건이
  `unsupported_number`** 이고 전부 검색 점수가 높다(0.854~0.901).
  게다가 **실행마다 달라진다** — 같은 문항이 재실행에서는 통과했다.
  생성이 어떤 수치를 내놓느냐에 달렸기 때문이다. 어떤 수치가 거부됐는지
  리포트에 남기지 않고 있어 진단이 불가능했다 → `unsupported_numbers` 를
  실패 기록에 넣었다. 이게 과한 검사인지 모델이 실제로 지어낸 것인지는
  다음 실행의 기록으로 가린다.
- en·vi 의 **무근거 표본이 2건·1건뿐**이다. 위 100% 는 신뢰 구간이 없는
  값이므로 두 임계값은 잠정이다. 골든셋 160문항 확장 때 언어별로 채운다.

## 2026-08-19 — 개발 환경을 Windows/CUDA 로 옮기고 MPS 를 걷어냈다

### 실측값

- **RTX 5060 Ti (sm_120 Blackwell, VRAM 15.9GB)** — torch 2.13.0+cu132.
  워밍업 후 4096³ matmul: **fp32 17.3 / bf16 60.9 TFLOP/s**. SDPA bf16 정상.
  `torch.cuda.get_arch_list()` 에 `sm_120` 포함 — "no kernel image" 함정 없음.
- **fastembed(e5-large) GPU 전환 효과 32.4배** — 32건 임베딩 GPU 88ms / CPU 2,857ms.
  MiniLM 64건은 GPU 43ms / CPU 664ms (15.4배).
  GPU·CPU 결과 일치도 cosine ≥ 0.99999985, maxdiff 1.8e-03 — 검색에 영향 없는 수준.
- **torch 와 onnxruntime CUDA EP 가 한 프로세스에서 공존한다.** import 순서 무관.
  cuDNN 이 두 벌(torch 9.20 / nvidia-cudnn-cu13 9.24) 깔려도 충돌하지 않았다.

### 결정과 근거

- **개발 장치를 MPS → CUDA 로 옮기고 MPS 경로를 제거했다 → [ADR-005](adr/ADR-005-cuda-only-dev.md).**
  ADR-004 의 "개발 mps / 배포 cuda" 이중 경로를 대체한다. dtype 이 개발·판정·배포
  모두 bf16 으로 통일돼, `report_charts` 가드가 막던 비교 불능 구간이 사라진다.
  **단 VRAM 은 18GB → 16GB 로 오히려 줄어** 1차 3종 중 Qwen3.5-4B 만 bf16 으로
  올라간다. 3종 전량 비교는 int8 실측 결과에 달려 있다.
- **int8 이월 사유가 해소됐다.** 8.7배 지연은 MPS 에 int8 행렬곱 커널이 없어서였다.
  CUDA 에서 재측정하면 4.87GB × 3 으로 3종을 모두 올릴 수 있다.

### 막힌 지점과 해결

- **`chroma-hnswlib 0.7.6` 이 Windows+py3.12 에서 소스 빌드로 떨어진다.** cp37~cp311
  win_amd64 휠만 배포되고 **cp312 는 없다**(Linux/macOS 는 있다). chromadb 0.5.20~1.1
  이 이 버전을 하드핀해 우회 불가. 빌드에는 pybind11 3.x 가 붙어 MSVC 2019+ 를
  요구하는데 이 PC 엔 MSVC 14.16(VS2017)뿐이었다 →
  **VS18 BuildTools 에 C++ 워크로드 추가(MSVC 14.51)로 해결.** Docker 는 무관하다.
- **`ort.get_available_providers()` 가 거짓말을 한다.** `onnxruntime-gpu` 설치 후
  `CUDAExecutionProvider` 를 보고하지만 **실제 세션 생성은 실패**하고 조용히 CPU 로
  떨어진다. 원인은 nvidia-* pip 패키지의 DLL(`cublasLt64_13.dll` 등)이
  `site-packages/nvidia/cu13/bin/x86_64/` 에 있어 Windows 검색 경로에 없기 때문.
  **`onnxruntime.preload_dlls()` 를 세션 생성 전에 불러야 한다.**
  providers 문자열만 보고 "GPU 붙었다"고 판단하면 32배를 그냥 잃는다.
- **양자화 ONNX 그래프가 sm_120 에서 깨진다.** `bge-small-en-v1.5`(`model_optimized.onnx`)
  의 fused `Attention` 이 cuDNN Flash Attention 그래프 빌드에 실패한다.
  `ORT_DISABLE_*_FLASH_ATTENTION` 우회도 안 먹는다. **비양자화(`model.onnx`)는 정상**이라
  실사용 모델(e5-large)은 무관하지만, 리랭커를 ONNX 양자화본으로 켜면 같은 벽에 부딪힌다.
  AWS(g5=sm_86 / g6=sm_89)에서는 재현되지 않을 것으로 본다.

### 기획서와 어긋난 지점

- **`requirements.txt` 가 Windows 에서 CUDA torch 를 재현하지 못한다.** PyPI 의
  win_amd64 휠(116MB)은 CPU 전용이고, 현재 깔린 `+cu132` 는 PyTorch 인덱스에서
  수동 설치한 것이다. Linux 휠은 `nvidia-cu13` 을 자동 동반해 문제가 없다.
  ADR-005 가 "CUDA 실측으로만 판정한다"고 못박은 이상 **팀원이 조용히 CPU torch 로
  측정하는 사고**가 가능하다 → 일단 requirements.txt 에 경고와 인덱스 URL 명시,
  근본 해결은 `requirements-base / -cpu / -gpu` 분할(후속).
- **pip 26.2 가 문서가 가정한 버전을 백트래킹으로 낮췄다.** requirements.txt 주석은
  "충돌 경고가 뜨지만 실동작 정상"이라고 적혀 있으나, 실제로는 경고 대신 더 낮은
  버전이 선택됐다: **chromadb 0.5.23 → 0.5.20** (0.5.23 의 `tokenizers<=0.20.3` 이
  transformers 5.15 와 충돌), **xgrammar 0.2.4 → 0.2.3** (0.2.4 의 `transformers<5`).
  `pip check` 는 깨끗하다. 순수 파이썬 핀이라 Docker 에서도 같게 해소된다 —
  환경이 깨진 게 아니라 **주석이 낡았다.** 단 Recall@5 93.9% 는 0.5.23 기준 수치라
  0.5.20 에서 재확인이 필요하다(`--no-generation`, 17분).
- **`fastembed~=0.4` 가 0.8.0 으로 해소됐다.** `cuda` 기본값이 `Device.AUTO` 로 바뀌어
  **CUDA EP 가 살아 있으면 코드 수정 없이 GPU 를 잡는다.** 편리하지만 로컬만 GPU 가
  되어 Docker(CPU)와 갈라진다는 뜻이기도 하다.
- **weasyprint 가 Windows 에서 임포트 실패한다**(`libgobject-2.0-0` 없음). GTK 런타임이
  따로 필요하다. M1 에서 쓰지 않으므로 방치하되, Dockerfile 은 이미 apt 로 해결돼 있다.

## 2026-08-19 (이어서) — 문법 생성이 스스로 멈추지 않고 있었다

ADR-005 후속 4건을 진행하다 성능 버그를 찾았다. 앞 절의 장치 전환이 없었으면
드러나지 않았을 종류다 — MPS 에서는 전량 채점 자체가 불가능해 이 구간을 볼 수 없었다.

### 실측값

- **XGrammar 사용 시 생성이 `max_new_tokens` 까지 스텝을 다 돈다.** 문법이 JSON 을
  닫아도 transformers 의 EOS 정지가 걸리지 않는다. 남는 스텝은 전부 EOS 이고
  `skip_special_tokens=True` 가 지우므로 **출력은 정상으로 보인다.**

      문법  cap    소요      실제스텝   그중 EOS   보이는 토큰
      없음  2048   12.1초        72          1        70   ← 정상 종료
      있음   512   79.1초       512        198       309
      있음  2048  305.6초      2048      1,734       309   ← 85% 낭비

  `GrammarMatcher.is_terminated()` 를 보는 `StoppingCriteria` 로 고쳤다:
  **cap 512 → 50.3초 / cap 2048 → 51.0초, 둘 다 316스텝, 출력 sha1 동일.**
  앱 경로(bench_local_speed) 기준 **⑦ 151.6초 → 31.7초, 체감 153.2 → 35.2초.**
- **문법 자체의 오버헤드는 4% 뿐이다** (cap 64 에서 12.58 → 12.05 tok/s).
  느렸던 것은 문법이 아니라 **멈추지 않는 것**이었다. 두 번 헛다리를 짚었다 —
  처음엔 "2048 토큰을 다 생성한다"(→ 실제 생성은 69토큰), 다음엔 "문법 커널이
  느리다"(→ 4%). **추론 말고 스텝 수를 직접 셌을 때 원인이 나왔다.**
- **int8 은 장치 아티팩트가 맞았다.** MPS 8.7배 → CUDA 1.18배(③ 1.7 vs 2.0초).
  다만 int8 은 cuda 에서도 ⑦ 이 1.32배 느리다 — **속도 대책이 아니라 용량 대책**이다.
- textonly 8.43GB / int8 4.87GB — 2026-08-18 MPS 기록과 **디스크 수치는 정확히 일치**.
  장치와 무관한 값이었음이 확인됐다.
- 모델 적재 VRAM 9,960 MiB (textonly bf16) — 16GB 에 예상대로 들어간다.

### 막힌 지점과 해결

- **XGrammar 의 CUDA 경로가 Triton 을 요구한다.** 없으면 생성 스레드에서
  `ImportError: Triton is not installed` 가 나고 **본 스레드는 그대로 멈춘다** —
  에러 메시지 없이 10분 행으로 관측됐다. Linux 는 torch 가 triton 을 자동 동반하지만
  PyPI `triton` 에 Windows 휠이 없다 → `triton-windows` 로 해결.
  이렇게 하면 Windows 도 Linux 와 **같은 triton 백엔드**를 타 ADR-005 의 "같은
  코드 경로"가 유지된다.
- **`torchao` 가 선언돼 있지 않았다.** `export_local_model.py --stage int8` 이 쓰는데
  requirements 에 없어 실행 시점에 `ModuleNotFoundError` 로 처음 발견됐다.
  int8 경로가 이 환경에서 한 번도 돈 적이 없다는 뜻이다.
- **`cache_implementation="dynamic"` 은 효과가 없었다** (276초, 기본값과 동일).
  KV 캐시 할당 가설은 틀렸다.

### 기획서와 어긋난 지점

- **`corpus/chunks.jsonl` 이 71청크다.** requirements 주석과 planner 는 "~1,200 청크"를
  전제한다. `corpus/processed/` 22개 문서에서 나온 값이라 파이프라인은 정상이고,
  **문서 쪽 수치가 실제와 다르다.** Recall@5 는 이 코퍼스 기준이다.
- **requirements 3분할** — `requirements-base / requirements(CPU) / requirements-gpu`.
  Dockerfile 이 `-r requirements-base.txt` 를 못 찾아 죽지 않도록 두 파일을 COPY 하게
  함께 고쳤다.

### 골든셋 160문항 전량 채점 완주 (exp_011)

ADR-004 가 "MPS 에서 4~6시간이라 사실상 불가능 → AWS GPU 가 있어야 판정된다"며
미뤄 둔 결정 게이트를 **로컬 CUDA 에서 80분에 완주했다.**

- **통과**: 인용 100%(60/60) · 숫자 100%(60/60) · 언어일치 100%(60/60) ·
  금지표현 0건 · Recall@5 93.5%(86/92, 목표 92)
- **미달**: 과잉폴백 43.5%(목표 8) · 폴백사유일치 60.3% · 계층일치 71.7% ·
  폴백정확 88.2% · 사실포함 85.1% · 지연 p50 23.3초(목표 6초)

**환각 방어는 만점인데 "답할 수 있는데 답하지 않는" 쪽이 전부 무너졌다.**
과잉폴백 40건 = `unsupported_number` 18 · `upstream_error` 12 ·
`language_mismatch` 6 · `low_confidence` 4.

`upstream_error` 12건은 모델 품질이 아니라 **JSON 잘림 버그**다. 걷어내면
과잉폴백 43.5% → **30.4%**, 지연 p95 149초 → **54초**.

⚠ **exp_009(MPS)와 섞지 않는다.** 같은 vi 41문항인데 과잉폴백이
66.7%(mps/fp16) → 71.4%(cuda/bf16) 로 움직였다. dtype 이 달라 생성이 갈린 것이고,
`report_charts.require_same_device()` 가 막으라고 있는 혼입이다.
**exp_011 이 새 기준선이다.**

### 과잉 폴백 43.5% → 25.0% (exp_012) — 두 버킷이 한 원인이었다

exp_011 의 최대 미달 항목을 잡았다. `upstream_error` 와 `unsupported_number` 는
따로 보였지만 **뿌리가 같았다** — 모델이 `numbers_used` 에 날짜를 `2025`,`3`,`21` 로
쪼개 넣다가 같은 값을 무한 반복하는 것.

### 실측값

| 지표 | exp_011 | exp_012 |
|---|---|---|
| **과잉 폴백** | 43.5% (40/92) | **25.0% (23/92)** |
| 정상 답변 | 60건 | **79건** (+19) |
| upstream_error | 13 | **1** (−12) |
| unsupported_number | 20 | **12** (−8) |
| 지연 p95 | 149초 | **45초** |
| 전량 소요 | 91분 | **54분** |
| 인용률·숫자정확도·금지표현 | 100 / 100 / 0 | **동일 (가드 유지)** |
| Recall@5 | 93.5% | 동일 |
| 폴백 정확도 | 88.2% | 85.3% (−2.9) |

언어별 과잉 폴백: **ko 30.6→8.2%(목표 8% 달성) · en 45.5→22.7% · vi 71.4→66.7%.**

### 막힌 지점과 해결

- **`numbers_used` 배열 폭주.** 스키마에 상한이 없어 모델이 같은 값을 무한 반복하다
  `max_new_tokens` 를 소진 → JSON 잘림 → 파싱 실패 → `upstream_error`.
  raw 를 떠보니 **답변 본문은 정상적인 A 등급**인데 뒤쪽 배열 하나가 폭주해 통째로
  버려지고 있었다. XGrammar 가 `maxItems` 를 문법에서 강제하는 것을 먼저 확인하고
  (`maxItems=3` 에서 4번째 거부) `numbers_used max_length=24`,
  `citations max_length=12` 를 넣었다. 반복 자체는 남지만 24개에서 닫힌다.
- **숫자 대조가 보여준 숫자를 차단.** 근거의 `100만원` 은 `1000000:krw` 로만 남아
  모델이 적은 맨숫자 `100` 과 만나지 못한다. 차단 20건을 근거 원문과 대조하니
  **18건이 오탐**이고 진짜는 `1350`(없는 전화번호)·`100,000` 둘뿐이었다.
  `numeral_supported` 에 `ctx.block`(모델에게 실제로 보여준 텍스트) 대조를 추가.
  ★ **경계 조건이 핵심이다** — 단순 부분문자열이면 근거의 `1000000` 안에서 거의
  모든 숫자가 매칭돼 가드가 무력해진다. 독립된 수 토큰으로만 인정한다.
  측정: 12/20 해소, **정탐 누출 0**.

### 남은 문제 — vi 는 코드로 못 고친다

vi 과잉 폴백 66.7% 의 최대 원인은 `language_mismatch` 7건인데, 재현해 보니
**모델이 실제로 한국어로 답한다**(한글 비율 0.68~0.90). 판정기 오탐이 아니다.

    Q-LIMIT-023  "한도제한계좌는 금융거래 목적을 확인할 수 없는…"  한글 86%
    Q-STAY-020   "대한민국에 입국한 날부터 90일을 초과하여…"       한글 90%

프롬프트는 이미 "반드시 {lang_name}로만 답변합니다"라고 명시한다. **Qwen3.5-4B 의
다국어 한계**이고, ADR-004 가 Sailor2-8B(SEA 특화, vi 포함)를 후보에 둔 이유가
여기서 확인됐다. 다만 bf16 ~17GB 라 16GB 에 안 들어간다 — int8 이 그 후보를 재기
위한 전제다.

### 방법에 대한 기록

원인을 두 번 헛짚었다. "cap 을 다 태운다"(→ 실제 생성은 69토큰), "문법 커널이
느리다"(→ 오버헤드 4%). **추측을 멈추고 raw 출력을 실제로 뜨고 스텝 수를 직접
세었을 때** 원인이 나왔다. 잘린 출력을 눈으로 본 것이 결정적이었다.

## 2026-08-20 — F2·F3·F4 를 관통시켜 필수기능 5/5 를 만들었다

F5 한 기능을 소수점 단위로 다듬는 동안 **필수 5개 중 3개가 코드 0줄**이었다.

### 결정과 근거

- **F2 기관 목록을 제도 근거에서 승격했다** (`spec-changes.md` #28).
  `institutions.yaml` 의 비자별 셀 4개가 전부 unknown 이라 그대로 만들면 카드가
  2장이고 전부 회색이다. 그런데 `common.mobile_arc` 는 **6개 은행을 이름으로
  열거**하고 비대면 가능 은행(신한·전북)까지 명시한다 — 그 열거가 기관 단위
  근거다. 4곳을 **같은 근거로** 추가했다. **새로 수집한 사실은 하나도 없다.**
  비자별 셀은 그대로 unknown 이라 3값 UI 시연도 산다.
- **F2 의 LLM 설명 문장을 M1 에서 뺐다** (#26). 조회 결과가 전부 unknown 이라
  생성 문장이 정적 문구보다 나을 것이 없는데, 카드마다 20~45초가 붙고
  vi 는 한국어로 답한다(exp_012). 부수 효과로 F2 는 **경로 전체가 규칙**이 되어
  답이 매번 같다 — 심사 시연에서 재현성이 보장된다.
- **지연 목표를 TTFT 로 재정의했다** (#27, ADR-004 갱신). 총 완료 P95 6초는
  생성이 API 였을 때의 값이고 로컬 4B 실측은 p95 44.7초다. planner §14.2 가
  애초에 TTFT 를 별도 지표로 두라 했고 계측도 있다 — **p50 3.5초 / p95 18.4초**.
  총 완료 시간은 참고 지표로 계속 기록한다.
- **F4 는 생성 경로를 새로 만들지 않았다.** `ChatPipeline` 이 ①~⑩ 을 이미
  관통한다. 이벤트 순서·`invalidate` 교체·폴백 처리를 두 벌 유지하면 한쪽이
  반드시 뒤처진다. `routers/chat.py::event_stream()` 에 `next_action` 인자
  하나를 더해 F4 가 같은 스트림을 탄다.
- **F4 는 질의를 한국어로 조립한다.** 챗봇 경로는 ③ 정규화가 이용자 언어를
  한국어 검색어로 옮기는데 그 품질이 en 86.4% / vi 90.5% 로 목표(92) 미달이다
  (ADR-004 §③). F4 는 질의를 **우리가 만들기 때문에** 정규화를 통과할 필요가
  없다 — 처음부터 정확한 한국어 검색어로 들어간다. 답변 언어는 `lang` 이
  정하므로 다국어성은 잃지 않는다.

### ★ 미확인을 0 점으로 접으면 근거 없는 주장이 점수가 된다

`fit_score` 산식(planner §9.2)을 그대로 옮기다 걸린 문제다.

    channel_access = 언어지원 0.5 + 비대면 0.3 + 전용지점 0.2

현 데이터는 `languages_supported: []`, `dedicated_branch_count: null` 이다.
이건 "없다"가 아니라 **"확인하지 못했다"**인데, 산식대로 0 을 넣으면
**확인 못 한 은행이 서비스가 나쁜 은행으로 정렬된다.** 근거 없는 주장을
정렬 순서로 만드는 것이고, 이 서비스가 가장 하지 말아야 할 일이다.

→ 미확인 항목은 **분자에서도 분모에서도 뺀다**(가중 평균을 아는 항목끼리만
   낸다). 무엇을 확인하지 못했는지는 `unverified` 로 함께 나가 카드에 그대로
   표시된다. 아는 항목이 하나도 없으면 `fit_score` 는 `0.0` 이 아니라 `null` 이다.

같은 함정이 `doc_burden` 에도 있었다. `required_docs: []` 를 "서류 0건(만점)"
으로 읽으면 **아무것도 모르는 은행이 1위가 된다.** 셀이 unknown 이면 이 항목
자체를 계산에서 뺀다.

측정: 현 데이터에서 순위를 가르는 것은 **확인된 비대면 여부 하나뿐**이다
(신한·전북 0.286 / 나머지 0.0). 그게 사실이므로 그렇게 나와야 맞다.

### ★ 성격이 다른 두 서류 목록을 한 표에 놓으면 은행에 재학증명서를 들고 간다

F3 의 서류 카탈로그를 만들며 원문 두 개를 확인했다.

    FSC-ACCOUNT-OPENING-PRACTICE   금융거래 목적 증빙 "예시" 표 (금융위) → 은행 창구
    HIKOREA-ARC-DOCS               체류자격별 외국인등록 제출서류 (법무부) → 출입국

D-2 의 재학증명서는 **후자**다. 앞에 섞으면 이용자가 그걸 들고 은행에 간다.
발급 기관도 제출처도 다르다 → `documents.yaml` 에서 절을 분리하고, PDF·화면
양쪽에서 "③ 외국인등록 제출서류 — **은행 서류가 아닙니다**"로 표기한다.

★ **금융위 표는 원문이 "증빙 서류(예시)"다.** 확정 목록이 아니고 은행마다
다르다(`KFB-LIMIT-ACCOUNT` 가 명시). 예시를 확정 목록으로 보여주면 이용자가
창구에서 다른 서류를 요구받는다 → 절마다 주의문구를 함께 싣는다.

★ **근거가 없는 조합은 만들지 않았다.** 금융위 예시 표에 없는 거래목적
(학비·생활비·송금)은 **의도적으로 비어 있고, 빈 절을 지우지 않는다** —
"확인하지 못했다"는 것 자체가 답이다.

### 막힌 지점과 해결

- **★ WeasyPrint 는 `ImportError` 가 아니라 `OSError` 로 죽는다.** 모듈은 찾지만
  그 안에서 `libgobject-2.0-0` 을 dlopen 하다 실패한다(Windows, error 0x7e).
  `except ImportError` 만 잡아 두었더니 **500 이 나갔다.** `(ImportError, OSError)`
  로 고쳐 503 + 화면 내 체크리스트 폴백(§12.3)이 성립한다.
  로컬에서 503 은 정상이고, **컨테이너에서 503 이 나오면 Dockerfile 이 깨진 것**이다.
- **★ Dockerfile 이 `corpus/matrix/` 를 복사하지 않았다.** 용어 사전과 **똑같은
  이유로** 빠뜨리면 배포에서만 `SystemExit` 가 난다 — 2026-08-12 에 한 번 겪은
  사고의 재판이다. F2·F3 를 붙이면서 COPY 를 함께 넣었다.
- **조판 검증이 오탐했다 — 레벨을 로거에 걸어서.** `fontTools.subset` 같은
  **자식 로거는 자기 레벨로 판정한 뒤 부모의 핸들러로 전파**하므로, 부모 로거를
  WARNING 으로 올려도 자식의 INFO 가 그대로 들어온다.
  `"Compiling 'glyf' table"` 308건이 그 경로로 잡혀 검증이 실패했다.
  → 레벨을 **핸들러**에 건다. (`scripts/check_typeset.py` 에 같은 형태가 남아
    있으나 렌더량이 적어 아직 드러나지 않았다.)
- **pdfplumber 의 `char["text"]` 는 2글자 이상일 수 있다**(합자). 그대로
  `unicodedata.combining()` 에 넘겨 `TypeError`. 길이를 보고 넘긴다.
- **가이드 테스트가 로컬 8GB 모델을 적재하려 했다.** F4 가 `/chat` 과 **같은**
  파이프라인 인스턴스를 쓰므로 `routers.chat._pipeline` 한 곳을 가짜로 바꾸면
  두 경로가 함께 격리된다(기존 `test_pipeline.py` 의 `FakeLLM`·`FakeRetriever` 재사용).
- **정렬 기준의 산문이 vi 화면에 한국어로 떴다.** `fit.py` 의
  `excluded_inputs`·`unverified_handling` 은 한국어 고정이다. 체크리스트
  주의문구와 같은 문제 → **산문은 화면의 i18n 이 갖고, 숫자(가중치·산식)만
  서버에서 온다.** 어긋나면 안 되는 값은 여전히 단일 출처다.
