# ADR-003: 임베딩 모델과 배포 메모리

- 상태: **채택** (단, 배포 등급 결정은 운영자 판단 필요)
- 날짜: 2026-08-12
- 관련: planner §2.2, §15.3 / 계획서 §0.1-B 메모리 게이트

## 맥락

계획은 **BGE-m3 로컬 실행**을 상정했다. Render 무료/스타터(512MB)에 올릴 수
없다는 것은 계획 단계에서 이미 인지했고, 1주 차에 컨테이너 실측 게이트를
세워 두었다. 이 문서가 그 게이트의 결과다.

착수 후 드러난 제약: **fastembed 는 BGE-m3 를 지원하지 않는다**(2026-08 기준).
BGE-m3·KURE 를 쓰려면 `sentence-transformers`(torch) 가 필요하고, 이는 이미지
크기와 메모리를 더 키운다. 그래서 fastembed 가 제공하는 다국어 3종으로 범위를 좁혔다.

## 실측

### 모델별 메모리 (로컬, RSS 최대치, 워밍 후 쿼리 1건)

| 모델 | 차원 | RSS | 로드 |
|---|---:|---:|---:|
| paraphrase-multilingual-MiniLM-L12-v2 | 384 | **820 MiB** | 13.4s |
| **intfloat/multilingual-e5-large** | 1024 | **1,510 MiB** | 3.8s |
| paraphrase-multilingual-mpnet-base-v2 | 768 | 1,987 MiB | 40.5s |

> **mpnet 은 모든 면에서 열등하다** — e5-large 보다 메모리가 크고(+477 MiB),
> 로드가 10배 느리며(40.5s), 차원은 낮다. 후보에서 제외한다.

### 컨테이너 실측 (e5-large, Docker)

| 상태 | 메모리 |
|---|---:|
| 유휴 (모델 미로드) | 46 MiB |
| 첫 질의 후 | 1,979 MiB (1.93 GiB) |
| 5회 추가 질의 후 | 1,980 MiB — **누수 없음** |
| **피크** | **2,096 MiB** |

- 첫 질의 15.0초 (컨테이너 내 모델 로드) / **웜 질의 0.08초**
- 이미지 크기 5.02GB (모델 캐시 동봉)

### ★ 결정적 발견 — 작은 모델은 안전장치를 없앤다

메모리만 보면 MiniLM 이 답이다. 그러나 임계값 보정을 다시 돌리면:

| 모델 | 코퍼스 안 최소 | 코퍼스 밖 최대 | **분리 폭** |
|---|---:|---:|---:|
| e5-large | 0.8494 | 0.8293 | **+0.0200** |
| MiniLM | 0.4099 | 0.6841 | **−0.2742** |

**MiniLM 에서는 두 분포가 겹친다.** 코퍼스에 근거가 없는 질의가 있는 질의보다
높은 점수를 받는다. 즉 `low_confidence` 폴백 판정이 **원리적으로 불가능**해진다.

이건 "품질이 조금 떨어진다"가 아니다. planner §6.6 의 검색 신뢰도 임계값이
통째로 죽고, "근거가 없으면 답하지 않는다"는 이 서비스의 핵심 주장 하나가
사라진다. 메모리와 맞바꿀 수 있는 것이 아니다.

## 결정

**`intfloat/multilingual-e5-large` 를 유지한다.**

- 배포 등급: **Render Standard(2GB) 이상 필요.** 스타터(512MB)는 불가능.
- 단, 피크 2,096 MiB 가 2,048 MiB 를 **근소하게 넘는다.** Render 의 계측
  기준이 cgroup peak 과 다를 수 있으므로 **배포 후 실제 인스턴스에서 재측정**하고,
  OOM 이 나면 아래 폴백을 실행한다.

### 폴백 계획 (Standard 로 부족할 경우)

우선순위대로:

1. **ONNX 세션 메모리 제한** — fastembed 가 쓰는 onnxruntime 의 arena
   할당을 줄인다. 코드 변경만으로 수백 MiB 를 줄일 여지가 있다. 미검증.
2. **MiniLM + LLM 리스코어링** (planner §6.5 2안) — 검색은 MiniLM(820 MiB)으로
   하고, **신뢰도 판정을 소형 모델 1회 호출로 대체**한다. 임계값이 죽는 문제를
   다른 신호로 메우는 것이며, 지연 +0.6~1.0초와 호출 비용이 든다.
   메모리를 1.2 GiB 수준으로 낮출 수 있다.
3. Render Pro(4GB) 전환 — 월 $85. 개인 참가에서는 마지막 수단.

**2번이 실질적인 대안이다.** 계획서 §6.5 가 리랭커 도입을 3주 차 결정 게이트로
둔 것이 여기서 의미를 갖는다 — 리랭킹은 품질 개선책이자 **메모리 예산을 사는
수단**이기도 하다.

## 검토했으나 기각

| 대안 | 기각 사유 |
|---|---|
| BGE-m3 (`sentence_transformers` 백엔드) | fastembed 미지원. torch 가 이미지와 메모리를 더 키운다 — e5-large 도 넘치는 상황에서 방향이 반대다. `EMBED_BACKEND=sentence_transformers` 로 교체 가능하게는 열어 두었다 |
| mpnet-base | 위 표 참조 — 모든 지표에서 e5-large 에 열등 |
| MiniLM 단독 | 신뢰도 게이트 소멸 (위 참조) |
| 임베딩 API 사용 | 검색 계층까지 외부로 나가면 ADR-002 의 "검색·판정은 전부 로컬" 주장이 무너진다 |

## 되돌리는 방법

`.env` 의 `EMBED_MODEL` / `EMBED_BACKEND` 를 바꾸고
`python corpus/scripts/04_index.py --rebuild` 를 실행한다.
**반드시 `python -m app.rag.cli --calibrate` 로 임계값을 다시 잡아야 한다** —
모델이 바뀌면 점수 척도가 통째로 달라지고, 이 문서의 −0.2742 가 그 증거다.

## 후속 (2026-08-12) — 리랭커를 얹지 않으므로 이 예산이 그대로 유효하다

리랭커 도입을 검토하면서 `bge-reranker-base`(1.04GB) / `jina-reranker-v2`
(1.11GB)를 얹으면 피크가 약 3.1GB 가 되어 **Render Pro(4GB) 상향이 필요**했다.
ADR-001 에서 **미도입으로 확정**했으므로 상향은 불필요하고, 아래 실측
(피크 2,096 MiB)과 `plan: standard` 가 그대로 유지된다.

덧붙여, 이 문서가 MiniLM 을 기각한 근거("신뢰도 게이트 소멸")는 여전히 유효하되
**측정 기준 하나가 교정됐다.** 당시 분리 폭은 코퍼스 밖 질의에 계층 C 함정을
섞어 잰 값이다. 게이트가 책임지는 것은 "근거 없음"뿐이므로(ADR-001), MiniLM 을
다시 검토한다면 그 기준으로 재측정해야 한다. e5-large 유지 결론 자체는
메모리·로드시간 항목만으로도 바뀌지 않는다.

## 🔄 배포 대상이 Render → AWS 로 바뀌었다 (2026-08-12, ADR-004)

아래 메모리 판단은 **Render Standard(2GB)** 를 전제로 한다. 배포가 AWS 서울
리전 GPU 인스턴스(g5/g6)로 옮겨가면서 그 전제가 사라진다.

- e5-large 1,510 MiB 는 GPU 인스턴스의 시스템 메모리에서 **더 이상 제약이
  아니다.** e5-large 를 GPU 에 올릴지(검색 지연도 함께 내려간다)는 실측 후 결정.
- **MiniLM 기각 근거는 그대로 유효하다** — 메모리가 아니라 신뢰도 게이트가
  무너지기 때문이었다. 다만 그 측정은 계층 C 함정을 무근거와 섞어 잰
  값이므로(ADR-001 참조), 재검토한다면 교정된 기준으로 다시 재야 한다.
- 로컬 생성 모델(4B fp16 ≈ 8GB)이 더해지므로 메모리 표는 **AWS 기준으로
  다시 작성**해야 한다. 아직 실측이 없어 지금 고쳐 쓰지 않는다.

## 미해결

- **AWS GPU 인스턴스에서의 메모리·지연 실측** (e5-large + 로컬 LLM 동시).
  로컬 Docker(colima) 계측이 그대로 옮겨간다는 보장이 없다.
- 이미지 5.02GB 는 빌드·배포 시간을 늘린다. 모델 캐시를 볼륨으로 빼면
  줄지만 콜드스타트에 런타임 다운로드가 생겨 §15.3 과 충돌한다.
