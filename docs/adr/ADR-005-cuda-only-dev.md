# ADR-005 — 개발 장치를 MPS 에서 CUDA 로 옮긴다 (단일 경로)

- 상태: **확정** — 개발·판정 모두 로컬 CUDA(RTX 5060 Ti 16GB)에서 bf16 으로 돈다.
  MPS 경로는 코드에서 제거했다.
- 날짜: 2026-08-19
- 대체: **[ADR-004](ADR-004-local-llm.md) 의 "개발 mps / 배포 cuda" 이중 경로 결정을
  대체한다.** ADR-004 의 나머지(로컬 생성 노선, 후보 3종, 판정 기준)는 유효하다.
- 관련: planner §2.3, §14.1 ·
  [로컬 생성 노선 확정 및 모델 비교 계획](../2026-08-17-local-llm-plan.md) ·
  [모델 슬림화](../2026-08-18-model-slimming.md)
- 측정: `eval/reports/exp_008_*_mps_*.json`, `exp_009_*_mps*.json` (폐기된 장치의 기록)

## 맥락

ADR-004 는 개발을 `device=mps`(M3 Pro 18GB), 배포를 `device=cuda`(AWS g5/g6)로
두고 **같은 코드 경로**로 양쪽을 돌린다고 적었다. vLLM 을 배제한 이유도 그것이었다
— MPS 를 지원하지 않아 개발과 배포가 갈라지기 때문이다.

그런데 ADR-004 자신이 그 구조의 실패를 기록해 두었다.

> **MPS 는 스크리닝, CUDA 는 판정.** dtype 이 장치마다 달라(mps fp16 / cuda bf16)
> 생성 결과를 한 표에 놓을 수 없다.

> **골든셋 160문항 전량 채점은 MPS 에서 4~6시간이 걸려 사실상 불가능하다.**
> 계획했던 결정 게이트를 로컬에서 실행할 수 없다 — **AWS GPU 가 있어야 판정된다.**

즉 "같은 코드 경로"는 코드 수준에서만 참이었고, **측정 수준에서는 이미 갈라져
있었다.** MPS 는 판정에 쓸 수 없는 장치였으므로 실질적으로는 스크리닝 전용
보조 경로였고, 다음 대가를 치르고 있었다.

1. **dtype 분기** — `resolve_dtype` 이 mps 에 fp16 을 주어 판정 dtype(bf16)과 달랐다.
   `report_charts.require_same_device()` 라는 가드를 따로 둬야 했던 원인이다.
2. **로드 경로 분기** — MPS 에서 `device_map` 이 SIGSEGV 를 내서 cuda 만
   `device_map` 을 쓰고 mps 는 `.to()` 로 올렸다. 최대 메모리가 두 배가 되는 경로다.
3. **int8 판정 불가** — MPS 에 int8 행렬곱 커널이 없어 매 연산마다 fp16 으로
   역양자화한다. `textonly-int8`(4.87GB)이 8.7배 느려 **탈락이 아니라 이월**로
   남았고, 결론이 나지 않은 채 AWS 를 기다리고 있었다.
4. **결정 게이트 정지** — 위 인용대로 160문항 채점이 로컬에서 불가능해,
   AWS 인스턴스를 띄우기 전까지 모델 확정이 진행되지 않았다.

한편 개발 환경에 CUDA GPU(RTX 5060 Ti 16GB, sm_120)가 확보되었다. bf16 실측
60.9 TFLOP/s, SDPA 정상 동작을 확인했다.

## 결정

**개발 장치를 CUDA 로 옮기고 MPS 경로를 코드에서 제거한다.**

- `resolve_device()` 는 `cuda` → `cpu` 만 반환한다. `cpu` 는 폴백이 아니라
  **등가성 검사 전용**(`scripts/check_equivalence.py`)이며, 자동 선택으로 잡히면
  경고를 남긴다. mps 가 있던 자리라 조용히 넘어가면 원인 추적에 시간을 버린다.
- `resolve_dtype()` 은 cuda 에 bf16 을 준다. **개발·판정·배포가 같은 dtype 이다.**
- `local_device` 타입에서 `"mps"` 를 뺀다.
- 판정도 이 장치에서 한다. AWS 는 배포용으로만 남기고, 모델 확정을 위해
  인스턴스를 띄우는 전제를 없앤다.

## 근거

**① dtype 이 통일되어 비교 불능 구간이 사라진다.** ADR-004 가 "CUDA bf16 실측으로만
판정한다"고 못박은 것을 개발 장치까지 끌어올린 것이다. 스크리닝 결과와 판정
결과가 같은 표에 놓인다 — MPS 시절에는 원리적으로 불가능했다.

**② 결정 게이트가 로컬에서 돈다.** MPS 에서 4~6시간이던 160문항 채점이 CUDA 에서는
현실적인 시간으로 떨어진다. AWS 인스턴스 확보가 모델 확정의 선행 조건이 아니게
된다.

**③ int8 판정이 열린다.** MPS 커널 부재로 이월됐던 `textonly-int8`(4.87GB)을
실측할 수 있다. 이것은 부수 효과가 아니라 **VRAM 제약을 푸는 유일한 경로다** —
아래 제약 참조.

**④ 코드가 줄어든다.** dtype 분기, 로드 경로 분기, 장치별 예외 주석이 사라진다.

## 제약 — VRAM 16GB

**장치를 바꿔도 메모리 제약은 풀리지 않는다.** M3 Pro 18GB → RTX 5060 Ti 16GB 로
오히려 2GB 줄었다. ADR-004 의 1차 측정 세트 중 bf16 으로 올라가는 것은 하나뿐이다.

| 후보 | bf16 크기 | 16GB 적재 |
|---|---|---|
| Qwen/Qwen3.5-4B | ~10GB (textonly 8.43GB) | ✅ |
| google/gemma-4-e4b-it | ~16GB | ❌ |
| sail/Sailor2-8B-Chat | ~17GB | ❌ |

게다가 `.to()` 경로는 최대 메모리를 두 배로 만들어 4B 조차 들어가지 않는다 —
`device_map` 은 최적화가 아니라 **이 장치에서 4B 를 올리는 전제**다.

따라서 **1차 3종 전량 비교는 int8 실측 결과에 달려 있다.** int8 이 품질을 보존하면
4.87GB × 3 으로 세 후보가 모두 올라가고, 그렇지 않으면 gemma-4-e4b·Sailor2-8B 는
여전히 AWS 가 필요하다. ADR-004 의 "AWS 가 있어야 판정된다"가 **3종 전량 비교에
한해** 남는다.

## 감수하는 것

- **macOS 개발 환경을 포기한다.** Apple Silicon 에서 `LLM_BACKEND=local` 은
  이제 cpu 로 떨어져 사실상 쓸 수 없다. 로컬 생성을 건드리지 않는 작업(API·검색·
  프런트)은 영향이 없다.
- **sm_120 은 배포 타깃(AWS g5=sm_86 / g6=sm_89)보다 신형이다.** 커널 경로가 달라
  질 수 있다. 실제로 ONNX 양자화 그래프의 fused `Attention` 이 sm_120 에서 실패하는
  사례를 확인했다(비양자화 경로는 정상). 배포 전 AWS 에서 1회 검증이 필요하다 —
  이것은 ADR-004 의 "개발과 배포가 갈라진다" 우려가 **장치 세대 차이로 형태를
  바꿔 남은 것**이다.
- **Windows 에서 `requirements.txt` 가 CUDA torch 를 재현하지 못한다.** PyPI 의
  win_amd64 휠은 CPU 전용이라 조용히 CPU torch 가 깔린다. `requirements.txt` 에
  경고와 인덱스 URL 을 명시했으나, 근본 해결은 requirements 분할이다(후속).

## 후속 — 진행 상황 (2026-08-19)

1. **int8 실측 — ✅ 완료. 가설이 맞았다.**

   | 산출물 | ③ 정규화 | ⑦ 생성 | MPS 기록 |
   |---|---|---|---|
   | textonly (bf16, 8.43GB) | 1.7초 | 151.6초 | ③ 2.4초 |
   | textonly-int8 (4.87GB) | 2.0초 | 199.9초 | ③ 20.8초 |

   MPS 의 **8.7배** 격차가 cuda 에서 **1.18배**로 무너졌다 — int8 지연은 장치
   아티팩트였다. 다만 **int8 은 cuda 에서도 여전히 더 느리다**(⑦ 1.32배).
   torchao 의 weight-only int8 은 메모리를 줄이지만 연산 시 역양자화 비용이 남고,
   배치 1 생성에서는 그 비용이 대역폭 이득을 넘는다.

   → **판정: int8 은 속도 대책이 아니라 용량 대책이다.** 16GB 에 1차 3종을
   올리려는 목적에는 여전히 유효하나, 지연을 이유로 채택할 근거는 사라졌다.

2. **골든셋 160문항 전량 채점 — ✅ 완주** (`exp_011_qwen35-4b-textonly_cuda`).
   **ADR-004 가 "AWS GPU 가 있어야 판정된다"며 미뤄 둔 결정 게이트를 로컬에서
   실행했다.** 아래 ④ 를 고치기 전에는 13시간이 걸려 불가능했다. 실제 소요 ~80분.

   | 지표 | 값 | 목표 | |
   |---|---|---|---|
   | 인용률 | 100% (60/60) | 100 | ✅ |
   | 숫자 정확도 | 100% (60/60) | 98 | ✅ |
   | 답변 언어 일치 | 100% (60/60) | 95 | ✅ |
   | 금지표현 | 0건 | 0 | ✅ |
   | Recall@5 | 93.5% (86/92) | 92 | ✅ |
   | 사실 포함 | 85.1% | 90 | ❌ |
   | 폴백 정확도 | 88.2% (60/68) | 95 | ❌ |
   | 계층 일치 | 71.7% (43/60) | 90 | ❌ |
   | 폴백 사유 일치 | 60.3% (41/68) | 90 | ❌ |
   | **과잉 폴백** | **43.5% (40/92)** | **8** | ❌ |
   | 지연 p50 / p95 | 23.3초 / 149초 | 6초 | ❌ |

   **환각 방어는 완벽하고(인용·숫자·금지표현 만점) 검색도 목표를 넘겼다.
   무너진 것은 전부 "답할 수 있는데 답하지 않는" 쪽이다.**

   과잉 폴백 40건의 내역: `unsupported_number` 18 · `upstream_error` 12 ·
   `language_mismatch` 6 · `low_confidence` 4.
   → **`upstream_error` 12건은 모델 품질이 아니라 아래 ⑦ 의 엔지니어링 버그다.**
   그것만 걷어내도 과잉 폴백은 **43.5% → 30.4%**, p95 는 **149초 → 54초**가 된다.

   ⚠ **exp_009(MPS·vi 41문항)와 직접 비교하지 않는다.** 같은 vi 41문항인데
   과잉폴백 66.7%(mps/fp16) → 71.4%(cuda/bf16)로 움직였다. dtype 이 달라 생성이
   갈린 것이며, `report_charts.require_same_device()` 가 막으라고 있는 바로 그
   혼입이다. **exp_011 이 새 기준선이다.**

3. **requirements 분할 — ✅ 완료.** `requirements-base / requirements(CPU) /
   requirements-gpu` 3분할. Dockerfile 도 두 파일을 COPY 하도록 고쳤다.
   미선언 의존성 2건을 발견해 추가했다: `torchao`(int8 export), `triton-windows`.

4. **⚠ 새로 발견 — 문법 생성이 스스로 멈추지 않는다 (수정 완료).**

   XGrammar 를 쓰면 문법이 JSON 을 닫은 뒤에도 transformers 의 EOS 정지가 걸리지
   않아 `max_new_tokens` 까지 스텝을 계속 돈다. 남는 스텝은 전부 EOS 이고
   `skip_special_tokens=True` 가 그것을 지우므로 **출력은 정상으로 보인다.**

   | cap | 정지조건 없음 | 정지조건 있음 | 출력 |
   |---|---|---|---|
   | 512 | 79.1초 / 512스텝 | 50.3초 / 316스텝 | sha1 동일 |
   | 2048 | 305.6초 / 2048스텝 | 51.0초 / 316스텝 | sha1 동일 |

   cap=2048 에서 스텝의 **85%(1,734/2,048)가 EOS** 였다. 문법 없이 생성하면
   72스텝에서 정상 종료하므로 문법 경로 고유의 문제다. `GrammarMatcher.is_terminated()`
   를 보는 `StoppingCriteria` 로 고쳤다 — 앱 경로 실측 **⑦ 151.6초 → 31.7초**.

   ★ 이것은 `local_max_new_tokens` 를 낮춰서 고칠 수 없다. 비용이 cap 에 비례하므로
   낮추면 빨라지긴 하나 잘림 위험(1024 에서 겪은 사고)만 새로 진다.

5. **XGrammar 의 CUDA 경로는 Triton 을 요구한다.** 없으면 생성 스레드에서
   `ImportError` 가 나고 **본 스레드는 에러 없이 멈춘다.** Linux 는 torch 가 triton 을
   자동 동반하지만 PyPI `triton` 에 Windows 휠이 없어 `triton-windows` 를 쓴다.

6. **AWS 1회 검증** — 모델 확정 후 배포 타깃(sm_86/89)에서 동일 산출물을 확인한다.

7. **✅ 해결 — 문법이 JSON 을 닫지 못하던 문항 (`exp_012`).**

   원인은 `max_new_tokens` 가 아니라 **`numbers_used` 배열에 상한이 없던 것**이었다.
   모델이 같은 값을 무한 반복하다 cap 을 소진해 JSON 이 잘렸다. raw 를 떠서 확인:

       Q-OPEN-004  "2025","3","21","2025","3","20",… 무한 반복 (3,490자에서 잘림)
       Q-OPEN-009  "3,613" 무한 반복 (3,131자에서 잘림)

   **두 문항 모두 `answer` 본문은 정상적인 A 등급 답변이었다.** 뒤쪽 배열 하나가
   폭주해 통째로 버려지고 있었다.

   XGrammar 가 JSON Schema 의 `maxItems` 를 문법 차원에서 강제하는 것을 확인하고
   (`maxItems=3` 에서 4번째 항목 거부) 스키마에 상한을 넣었다:
   `numbers_used max_length=24` · `citations max_length=12`.

8. **✅ 숫자 대조가 "보여준 숫자"를 차단하던 문제.**

   정규형 집합끼리만 비교해 근거의 `100만원`(→`1000000:krw`)과 모델이 적은 맨숫자
   `100` 이 만나지 못했다. 차단 20건을 근거 원문과 대조하니 **18건이 오탐**이고
   진짜는 `1350`(없는 전화번호)·`100,000` 둘뿐이었다.

   `numeral_supported` 에 **모델에게 실제로 보여준 텍스트**(`ctx.block`) 대조를
   추가했다. 경계 조건이 핵심이다 — 단순 부분문자열이면 근거의 `1000000` 안에서
   거의 모든 숫자가 매칭돼 가드가 무력해진다. **독립된 수 토큰**으로만 인정한다.
   측정: 20건 중 12건 해소, **정탐 누출 0**.

9. **⚠ 남은 병목은 vi 이고, 코드로 고칠 수 없다.**

   `exp_012` 의 언어별 과잉 폴백: **ko 8.2%(목표 달성) · en 22.7% · vi 66.7%.**
   vi 14건의 최대 원인은 `language_mismatch` 7건인데, 재현해 보니 **모델이 실제로
   한국어로 답한다**(한글 비율 0.68~0.90). 판정기 오탐이 아니라 정탐이다.

       Q-LIMIT-023  "한도제한계좌는 금융거래 목적을 확인할 수 없는…"  한글 86%
       Q-STAY-020   "대한민국에 입국한 날부터 90일을 초과하여…"       한글 90%

   프롬프트는 이미 "반드시 {lang_name}로만 답변합니다"라고 명시한다. 근거 문서가
   전부 한국어라 구조적으로 끌리는 것도 있다. **Qwen3.5-4B 의 다국어 한계다.**

   → ADR-004 가 `sail/Sailor2-8B-Chat`(SEA 특화 SFT, vi 포함)을 후보에 넣은 이유가
   여기서 확인됐다. 다만 bf16 ~17GB 로 16GB 에 들어가지 않는다. **int8(4.87GB 급)이
   그 후보를 재기 위한 전제**다 — ①의 "int8 은 용량 대책"이 여기로 이어진다.

   `upstream_error` 13/160. 모델이 `local_max_new_tokens`(2048) 안에 JSON 을 닫지
   못해 잘리고, `LLMAnswer.model_validate_json` 이 실패해 폴백된다
   (`local_client.py` 가 "여기 오면 대개 생성 길이 초과"라고 이미 적어 둔 경로다).

   - 검색은 **정상**이다 — 실패 문항도 top1 0.88~0.90, gold 문서 전량 회수.
     생성만의 문제다.
   - 언어를 가리지 않는다: ko 5 · en 4 · vi 4.
   - 이 문항들의 지연 p50 은 **156초** — cap 2048 을 그대로 태운 값이다.
     ④ 의 정지 조건은 문법이 *종료될 때만* 듣는다. 종료되지 않는 이 경로는
     ④ 이전과 동일하게 cap 을 소진한다. **④ 가 만든 문제가 아니다.**
   - `local_max_new_tokens` 를 **올려도 해결되지 않을 가능성이 높다** — 1024 에서
     2048 로 올렸을 때도 같은 형태가 남았다(§config). 모델이 문자열 필드 안에서
     멈추지 못하는 것이라면 상한은 대책이 아니다.

   조사 순서: ① 잘린 raw 출력을 실제로 떠서 **어느 필드에서 늘어지는지** 확인
   → ② 프롬프트의 길이 지시/스키마 서술 문제인지, 문법 자체의 문제인지 분리
   → ③ 그 다음에야 상한·프롬프트·문법 중 무엇을 고칠지 결정.

## 폐기되는 기록

`eval/reports/exp_008_*_mps_*.json`, `exp_009_*_mps*.json` 은 **삭제하지 않는다.**
MPS 에서 나온 수치이며 cuda 리포트와 한 표에 놓을 수 없다. `report_charts.py` 의
`require_same_device()` 가드는 이 기록들 때문에 **그대로 유지한다** — 새 리포트끼리는
장치가 통일되어 사고가 나지 않지만, 과거 리포트와의 혼입은 여전히 가능하다.
