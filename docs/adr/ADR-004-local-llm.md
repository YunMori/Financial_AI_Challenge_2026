# ADR-004 — 로컬 생성 모델 (진행 중, GPU 실측 대기)

- 상태: **잠정** — 배선과 정확성은 확인, **성능 판정은 AWS GPU 실측 후**
- 날짜: 2026-08-12
- 관련: ADR-002(생성 LLM 선정) · ADR-001(리랭커) · planner §2.3, §14.1, §15.2

## 맥락

ADR-002 는 "감수하는 것"으로 **국내 리전 원칙 미충족**을 적어 두었다.
Anthropic API 가 해외 리전이기 때문이다. 생성을 로컬 모델로 내리고 배포를
**AWS 서울 리전(ap-northeast-2)** 으로 옮기면, planner §15.2 의 `LLM_REGION=kr`
은 문구 수정이 아니라 **실제로 충족**된다. 금융 도메인에서 데이터 주권은
서술로 덮을 수 있는 종류가 아니다.

비용은 부차적 동기다 — 골든셋 160문항 1회가 $1.59 로, 재충전으로 끝나는 문제다.

## 결정

**런타임: PyTorch + transformers + XGrammar, 단일 코드 경로**
(개발 `device=mps`, 배포 `device=cuda`).

vLLM 은 처리량이 좋지만 **MPS 를 지원하지 않아 개발과 배포가 갈라진다.**
이 프로젝트는 컨테이너 기동 실패와 조판에서 "로컬에선 됐는데" 사고를 이미
두 번 겪었다. 단일 사용자 데모라 처리량은 병목이 아니다.

**모델: `Qwen/Qwen3-4B-Instruct-2507`** (잠정).

> **Gemma 3 는 gated repo 라 401** — 라이선스 동의와 HF 토큰이 필요해 측정에서
> 제외했다. 접근이 열리면 비교군에 넣는다. 한국어 특화 소형 모델
> (EXAONE·HyperCLOVAX·Kanana)은 **ko/en 전용이라 후보가 아니다** — 공개 언어에
> 베트남어가 있다.

## 측정으로 확정된 사실

### ① 구조화 출력 — 선택 필드는 문법이 생략을 허용한다 ★

가장 중요한 발견이다. `LLMAnswer.citations` 는 `default_factory=list` 라 JSON
스키마의 `required` 에 들어가지 않는다. 문법은 그걸 그대로 반영해 **생략을
허용**하고, Qwen3-4B 는 `answer`·`tier`·`numbers_used` 를 채운 뒤
**`citations` 를 통째로 건너뛰었다.**

결과: 인용 0건 → 후처리가 차단 → **정상 답변이 `no_citation` 폴백**이 된다.

Anthropic 경로가 멀쩡했던 것은 **Claude 가 지시를 따라 채웠기 때문이지 스키마가
강제해서가 아니다.** 모델의 선의에 기대고 있던 자리였고, 모델을 바꾸자 드러났다.

→ 문법 컴파일 직전에 모든 속성을 `required` 로 만든다(`_require_all_fields`).
   **Pydantic 모델은 건드리지 않는다** — 파이썬 쪽 입력 관용은 유지하고 생성
   문법만 엄격하게 한다. 회귀 테스트 3종.

### ② `answer` 가 첫 필드인 설계가 길이와 충돌한다

`answer` 를 스키마 첫 필드에 둔 것은 스트리밍 TTFT 를 위한 의도적 설계다
(`app/schemas/llm.py`). 그런데 본문이 길면 `max_new_tokens` 를 소진해
**뒤따르는 `citations`·`numbers_used` 가 생성되기 전에 잘린다** — 역시
`no_citation` 폴백이다. **길이가 곧 차단 사유가 되는 구조**다.

→ `local_max_new_tokens` 1024 → 2048, 시스템 프롬프트에 **3~5문장·400자** 명시.
   "짧게"라는 지시만으로는 소형 모델이 길게 쓴다.

### ③ 정규화 품질 — 로컬이 낮다

Recall@5 (골든셋 160문항 중 해당 언어):

| | API (haiku) | 로컬 (Qwen3-4B) | 목표 |
|---|---:|---:|---:|
| en | 95.5% | **86.4%** | ≥92 |
| vi | 95.2% | **90.5%** | ≥92 |

프롬프트의 `E-9` **예시**를 Qwen3 가 **지시**로 읽어 질문에 없는 E-9 를 모든
검색어에 주입하던 것을 고쳐 vi 를 81.0% → 90.5% 로 올렸다. 둘 다 목표 미달이다.

> **용어표 주입은 시도했다가 되돌렸다.** 코퍼스 표준 용어 35개를 보여 주면
> 어휘가 수렴할 것으로 봤고 개별 검색어는 정확해졌다("한도제한계좌").
> 그런데 Recall@5 가 **떨어졌다**(en 59.1%, vi 76.2%) — 검색어가 짧고 좁아져
> dense 정보량과 BM25 후보 폭이 함께 줄었다. **용어가 정확한 것과 검색이 잘
> 되는 것은 다른 문제였다.**

### ④ 지연 — MPS 는 개발 도구이지 제품이 아니다

M3 Pro / MPS / Qwen3-4B fp16, **문법 없이도 11.4 tok/s**. XGrammar 가 병목이
아니라 장치 자체의 속도다.

| 질의 | 총 지연 | TTFT |
|---|---:|---:|
| ko (근거 5건) | 125.0s | 41.7s |
| en | 55.6s | 23.1s |
| vi | 42.2s | 15.5s |
| 계층 C 함정 | **0.0s** | — (규칙이 LLM 이전에 차단) |

**골든셋 160문항 전량 채점은 MPS 에서 4~6시간이 걸려 사실상 불가능하다.**
계획했던 결정 게이트를 로컬에서 실행할 수 없다 — **AWS GPU 가 있어야 판정된다.**

## 아직 결정하지 않은 것

- **모델 크기·최종 채택**: 4B 로 정규화가 목표 미달이다. 8B 로 올릴지,
  정규화만 API 로 남기는 하이브리드로 갈지는 GPU 실측 후 판단한다.
- **지연 목표**: 총 완료 시간 P95 6초는 로컬에서 재정의가 불가피하다.
  planner §14.2 가 애초에 **TTFT 를 별도 지표로** 두라고 했고 계측(`ttft_ms`)은
  넣어 두었다.

## 다음 단계

1. AWS g5/g6(ap-northeast-2)에서 `device=cuda` 로 골든셋 160문항 전량 채점
2. 게이트 판정: 인용률 100% · 숫자 정확도 ≥98% · 금지표현 0 · `numbers_used` 완전성
3. 미달 시 8B → 그래도 미달이면 생성만 API 로 되돌리는 하이브리드
4. ADR-002 개정(국내 리전 해소), ADR-003 을 AWS 기준으로 교체

## 현재까지의 판단

**정확성 경로는 살아 있다.** 문법 제약으로 형식이 보장되고, 필수 필드를 강제한
뒤로는 인용·수치가 정상적으로 생성된다(계층 A/B 판정, `numbers_used`
["30만원","100만원","300만원"] 정확). 계층 C 함정은 규칙이 0.0초에 차단한다.

**남은 것은 성능과 정규화 품질이며, 둘 다 하드웨어·모델 크기의 함수다.**
그래서 이 ADR 은 지금 확정하지 않는다 — 확정할 근거가 아직 없다.
